## 原理

### WeSing（进程内存读取）

```
WeSing.exe 进程
├─ KSongsLyric.dll → LyricHost 对象 → 歌词文本 + 时间戳
├─ 音频引擎 → float 播放时间（秒）
├─ 内存 JSON → "songname":"歌名","singername":"歌手"
├─ UI 进度文本 → "mm:ss | mm:ss"（歌曲总时长）
└─ 窗口层级:
   ├─ "全民K歌"（主窗口，TXGuiFoundation）
   ├─ "全民K歌 - 歌名"（播放窗口）
   └─ "CLyricRenderWnd"（歌词渲染窗口，歌曲加载完毕后出现）

PlayerCap (wesing 模块)
├─ 通过 PE 导出表 + vtable 搜索定位 LyricHost
├─ 解码歌词数据结构 (UTF-16LE)
├─ 同一个 LyricHost 里这首歌的音译轨（路径是主歌词那份文件对应的 _Roma.qrc；别的歌留下的不认）→ roma_text，
│  按行号 + 行起始时间配到主歌词上；
│  音译轨自己的字级单元连同时间 → roma_text_detailed
├─ AOB 特征搜索定位播放时间（结构体固定字段：单行排版 0x1E/0x2D，双行排版 0x1C/0x2A）；
│  通过校验的不止一个时挑读数正在走的那个（都不走就取读数不为 0 的），选定后若它停着而另一个在走就改用另一个；
│  落选的候选随这个地址一起沿用到之后的歌
├─ AOB 搜索 UI 进度文本提取歌曲总时长
├─ AOB 搜索内存 JSON 提取歌名+歌手
├─ 窗口状态机检测播放阶段（单次 EnumWindows）
├─ play_time 停滞检测 → 暂停/恢复事件
├─ 播放中每 5 秒向服务端报一次位置采样（内部事件 position_sample，不外发），校准连接补发与 HTTP 快照的位置
└─ 进程存活检测 → 断线自动重连
```

### CloudMusic（CDP 远程调试）

```
cloudmusic.exe 进程（Electron）
├─ --remote-debugging-port=9222
├─ React / Redux 状态 → 歌曲 ID、歌词、播放状态
└─ DOM → 歌名、歌手、封面、进度文本

PlayerCap (cloudmusicv3 模块)
├─ Watchdog 确保进程带调试端口启动（注册表注入自启参数）
├─ WebSocket CDP 客户端连接浏览器
├─ JS 求值 → React Fiber 遍历 → 提取 Redux + DOM 状态
├─ 切歌时强制 Redux 刷新歌词，优先使用当前歌曲 Redux ID
├─ DOM / Redux 双重校验，避免旧歌词、旧封面串到新歌
├─ 网易云 API / CDP 获取歌词（LRC 解析）+ 封面
├─ 本地时钟锚定 + seek 检测；界面进度（DOM 整秒值）跳秒的那一拍对表，保留约 0.3s 的落后量，
│  校准量达到 0.2s 时发 playback_resume
├─ Redux 播放状态（playingState）变化 → 暂停/恢复事件
└─ 播放中每 5 秒向服务端报一次位置采样（内部事件 position_sample，不外发）
```

### QQMusic（进程内存读取 + AOB Hook）

```
QQMusic.exe 进程
├─ QQMusic.dll + 0xC87C80 → 歌曲元数据（歌名/歌手/SongID/进度/时长）
├─ QQMusic.dll + 0xC157D8 → 快速计时器指针（~1秒更新）
├─ QQMusic_GFWrapper.dll → 伴奏滑块控件（AOB Hook 捕获 ESI/EDI）
└─ QQMusic.dll + 0x488B75 → 精确进度写入点（AOB Hook + KUSER 时间戳）

PlayerCap (qqmusic 模块)
├─ 进程内存扫描定位 QQMusic.dll + QQMusic_GFWrapper.dll
├─ AOB Hook 注入（伴奏滑块）
├─ 快速计时器锚点 + 本地时钟实时线性插值
├─ QQ 音乐 API 获取歌词（QRC 3DES 解密）+ 专辑封面
├─ 快速计时器异常跳变检测 seek（支持前跳 / 回跳）
├─ 快速计时器停滞检测 → 暂停/恢复事件
└─ 播放中每 5 秒向服务端报一次位置采样（内部事件 position_sample，不外发），校准连接补发与 HTTP 快照的位置
```

### KuGou（CDP 远程调试 + libcef patch）

```
KuGou.exe 进程
├─ libcef.dll → CEF / Chromium 内核
├─ DevTools 端口 12233（由 PlayerCap 自动 patch libcef.dll 打开）
├─ desktop-popup 页面 → external.SuperCall(864) 播放信息接口
└─ PlayInfo → hash、filename、cover、progress、duration、playStatus

PlayerCap (kugou 模块)
├─ Watchdog 自动定位酷狗安装目录（注册表 + Program Files 兜底）
├─ 检测 libcef.dll patch 状态，必要时终止酷狗 → 提权 helper patch → 重启酷狗
├─ WebSocket CDP 客户端连接 desktop-popup 页面（端口 12233）
├─ JS 求值调用 SuperCall 获取播放信息
├─ hash 变化检测切歌，filename 拆分歌名 + 歌手
├─ 酷狗歌词 API 获取歌词（hash 优先，必要时按歌名/歌手/时长解析 canonical hash）
├─ CDP 封面 URL + 酷狗公开 API 兜底获取封面，异步下载 Base64
├─ 本地时钟锚定 + 100ns progress 单位换算 + seek 检测
├─ 伴唱/伴奏等同曲 hash 变化时复用同名同歌手歌词
├─ 播放中每 5 秒向服务端报一次位置采样（内部事件 position_sample，不外发），校准连接补发与 HTTP 快照的位置
└─ play_time 停滞检测 → 暂停/恢复事件，CDP 断开后自动回到等待状态
```

### SodaMusic（CDP 远程调试 + 明文 KRC）

```
SodaMusic.exe 进程（Electron）
├─ 原生反调试：启动参数带 --remote-debugging-port 会被它自杀，故不能改 argv
├─ 命名映射 node-debug-handler-<pid> → 主进程里 inspector 激活函数的地址
├─ Node inspector 端口 9229（激活后由目标自己开，反调试不检测它）
├─ rendererMain 主窗口 → 字节的 transport 服务 → sharedState.get('player')
└─ 播放态：progressSeconds（1Hz 采样）、mediaDetail.playable（名/歌手/id/时长/封面）、
           mediaDetail.lyrics（明文 KRC + translations.cn 独立译轨）

PlayerCap (sodamusic 模块)
├─ Watchdog 找主进程 pid（命令行不含 --type= 的那个），复刻 process._debugProcess 开 9229
│  —— 只读命名映射 + 让目标跑它自带的激活函数，不改汽水任何内存/状态
├─ CDP 连 9229 主进程 Node context，executeJavaScript 桥进 rendererMain 取全量播放态
├─ 取数时顺带关掉该窗口的后台节流：汽水最小化且约 5 分钟无人交互后，Chromium 会把进度
│  刷新从 1Hz 压到 1/60Hz；这一步让它最小化时也保持 1Hz，设不上则告警一次而非静默降级
├─ mediaId 变化检测切歌；mediaDetail 未就绪（歌名为空）时跳过本轮，不发半成品
├─ 时长比歌名晚到时给 2 秒宽限，避免 all_lyrics 带着 duration=0 出去让进度条整首归零
├─ 歌词是平台已解密的明文 KRC，复用 player/krc 解析出逐字，连解密都省
├─ 翻译来自 translations.cn 的独立 tlyric LRC，按绝对时间戳（±10ms）合并进 sub_text
├─ 封面 URL 由 cover_url 的 {urls,uri,template_prefix} 拼成 800×800，异步下载 Base64
├─ 本地时钟外推：进度源只有 1Hz，仅在采样变化时落锚、两次采样之间按墙钟推进
│  —— 每轮都落锚等于没有外推，position 会退化成 1 秒阶梯、歌词整体滞后
└─ 播放中每 5 秒向服务端报一次位置采样（内部事件 position_sample，不外发），缓冲中照发
```

### Apple Music（进程内存读取 + iTunes TTML）

```
AppleMusic.exe 进程（WinUI3 + JSC，非 Node：sodamusic 那套 _debugProcess 开 inspector 的路子不通）
├─ 交给系统媒体会话（SMTC）的「正在播放」属性存储（MS-PROPSTORE）
│  → System.Title = 歌名；System.Music.Artist = 「歌手 — 专辑」（U+2014）；应用名段 = 「Apple Music」；
│    标题段里还带封面（图片字节流）
├─ iTunes TTML（UTF-16，命名空间 lyric-ttml-internal）→ 行、逐字（仅 Word 型）、译文（按 itunes:key 对齐）
├─ 位置结构 [时长][位置][位置]（float64 秒）→ 时长（真实音频时长、整数秒，与 SMTC EndTime 一致）、
│  位置（整秒推进、约 1Hz 刷新）；同一进程内地址不变，换歌时时长先归零，0.25s~数秒后写入新时长
└─ 出声的不是它：播放由同包的 AMPLibraryAgent.exe 完成（DCOM / svchost 拉起，不在 AppleMusic.exe 进程树内）

PlayerCap (applemusic 模块)
├─ 纯只读：OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ) + VirtualQueryEx + ReadProcessMemory，
│  不写目标一个字节；不走 SMTC / WinRT（用户要求纯内存、零 WinRT 依赖）
│  —— 普通权限即可（同用户、同完整性级别，2026-10-08 未提权会话实测）；拒绝访问时报 waiting_process + no_admin
├─ 全扫（mem.Reader.Scan）只读 MEM_PRIVATE 且保护属性恰为 PAGE_READWRITE 的已提交区，本机实测一次 0.12~0.24s
│  （2026-10-09，可读区 436MB：不收位置候选 0.12~0.16s，收 0.19~0.24s）；读缓冲跨全扫复用（超过 64MB 的扫完即丢），
│  逐窗找位置候选先按时长字段的原始位预筛；
│  全扫途中照常读位置、推歌词行（换歌本身会触发全扫，不读的话开播要等扫完才看见）
├─ 歌名 / 歌手 / 专辑 / 封面：按 MS-PROPSTORE 格式整条解析存储链，只认同一条链里同时有 System.Music 段与应用名段、
│  且链完整收尾的那份；「歌手 — 专辑」按第一个 " — " 拆；封面是标题段 #27 的 VT_STREAM（JPEG / PNG 字节）
│  —— 只凭 "1SPS" + System.Title 锚点会命中别的属性存储（审查方实测 18 处中 17 处是 Windows 设置项的搜索关键词）
├─ 多份存储按 (歌名, 歌手, 专辑) 归并，依次比：不是上一首期间就在的完整副本数（链首带媒体类别段的那种）、
│  带封面的完整副本数、完整副本数、歌手非空、不是上一首期间就在的副本数、总份数、是否当前曲目、字典序，
│  结果确定（pickNowPlaying）
│  —— 只比份数会挑错：真机上内存里残留着早先一首的 2 份非完整副本，当前歌只有 1 份完整副本，三次换歌三次宣告成旧歌
│  —— 完整副本分两种（2026-10-09 真机逐秒采样）：带封面的总是当前歌；不带封面的会残留（见过一份留了 2 分 40 秒、
│     跨三次换歌）。只比完整副本数时，当前歌一份带封面的、另一首一份不带封面的会平手、落到字典序：服务在这时
│     重启，或同一首从头再放，宣告成了另一首
│  —— 每次换歌约 0.1~0.25s 后，带封面的那份在新地址重建，或把原地址就地改写成新歌名。记下选中那份的地址与
│     开头 512 字节，每 300ms 复读，对不上就是「存储换了」，立刻全扫：时长相同的两首自然衔接、封面晚到都靠它发现
├─ 位置结构靠活性确认：未确认而已见到存储时，按退避（立即，然后 2/3/5/5s，封顶 15s）全扫收集同形态候选（时长为
│  15~7200 的整数秒，本机实测 400~530 个），之后每 300ms 复读候选：位置是整数、每次只走一格、相邻两格相隔 0.5~2.5s、
│  连着两次，并且内存里已见到存储，才认；确认后每轮只读这 24 字节
│  —— 形态相同的静止结构很多；Apple Music 刚启动时还有个 [100][进度][进度] 的进度条在走，只看「在不在走」会锁错
│  —— 候选时长变了（含归零）不删、重新计；存储换了而位置结构还没认出时，候选扫描重排到开头几档
│  —— 没见到存储时（Apple Music 启动后还没放过歌：真结构尚未分配、内存里也没有存储可盯）周期全扫只找存储、
│     不收候选（立即，然后 2/3/5s，封顶 5s；本会话第一次全扫照收），认出存储后立即补一次收候选的全扫，再加判活。
│     离线回放（假内存的全扫不耗时）从开播到宣告最坏 7.0s（存储与时长同时出现）、6.0s（存储早 1s 出现），
│     改动前同一回放为 17.0s 与 16.0s；真机端到端 2026-10-09 量到一次约 4s
│  —— 存储的出现 / 消失距上一次不足 10s 算抖动：只换间隔表，不回到开头几档、不立即补扫；存储还在、只换了歌名不算。
│     否则相邻两次全扫交替认出与认不出存储时，周期全扫停在约每 1.15s 一次（离线回放 10 分钟 521 次，现为 123 次）
├─ 确认位置结构之前不宣告任何歌：暂停中附加时位置不走、认不出，一直报 waiting_song + no_song；
│  按播放（或点别的歌）后候选在走即认出并宣告
├─ 位置结构停住 20s、或确认了 5s 还宣告不出歌，按退避全扫找别的在走的结构，防锁在陈旧副本或认错的结构上
├─ 已确认的位置结构连续 0.9s 读不出或形态不对即作废（twinFailFor）：在放则按暂停报，作废期间只报 paused；
│  重新认出的结构若时长与当前曲目相同即当作同一首：按恢复报，不重新宣告，歌词行号复位（找回的位置可能在
│  已推的行之前）；时长不同则按换歌处理
├─ 位置结构时长变化 → 换歌，新歌起手按在放（时长变正就是开播；暂停中切歌时时长一直是 0，按了播放才写入）；
│  加载中（时长为 0）不宣告，除超过 6s 清屏外不发事件；换歌 1.5s 后再全扫一次核对歌名，3s 内读到另一个歌名
│  按「首扫读到的是上一首」纠正，3s 之外读到则是时长相同的下一首、按新歌重来
├─ 进程在而没有歌 → waiting_song + no_song：附加后到第一次宣告之前；换歌加载中超过 6s（loadingGrace）；
│  换歌后 10s 仍取不到歌名（titleGiveUp，每轮都判，不等下一次扫描）。后两者另发 clear_song_data。
│  加载超时同时复位当前曲目，取不到歌名的仍按退避续扫、取到即宣告
├─ 歌词归属：TTML 里没有歌曲标识，按「文档最近一次在内存里出现新副本时存储里是哪首歌」记到那首歌名下，
│  覆盖原归属（新副本 = 这次全扫里有上一次全扫没有的副本地址，含第一次出现、整份消失后重新出现）；
│  <body dur> 只当上限（比位置结构时长长出 6s 以上的不用）——它是歌词正文的长度，可以比音频短得多
│  （真机：231.752 对 245、130.820 对 159）
│  —— 真机上每次一首歌成为当前曲目，它的文档都会出现新地址的副本（五次观察都是）；歌词会预取，预取的文档
│     先记在当时那首歌名下，轮到它自己时随新副本改记过来
│  —— 记在具体歌名下的文档留一份全文（至多 48 份，超出丢掉最久没在全扫里见到的），离开内存后仍可用；归属照旧
│     跟着改记与歌名纠正走，清屏、换歌都不清，重新附加后从空开始。真机上文档可能只在内存里待 1 秒：存储换成
│     新歌的同一秒它出现、下一秒整份消失，而那首歌起播慢（加载超过 6s 走了清屏），就绪时它早已不在内存里
│  —— 留存的那份只配给采用它时同一时长的曲目（改记到别的歌名下后重新算）：归属只看歌名与歌手，分不出同名
│     同歌手的两个版本，不核对时先放过短版、再放长版，留下的短版歌词会被长版采用且换不掉。没被采用过的
│     留存无从核对；还在内存里的文档不经这道核对
│  —— 上一首的 TTML 换歌后会残留，副本数也分不出新旧（审查方实测新旧两首各 4 份），按副本数挑会配错
│  —— 本会话第一次全扫只建基线：内存里已有的文档来历不明。来历不明的文档（附加前就在内存里的、出现时没认出
│     存储的）只有 <body dur> 比时长长 0~6s 才用；附加前就在的还只给本会话第一首（它们能在内存里留几分钟、
│     跨好几首），之后出现新副本才改记到当时那首歌名下
│  —— 局限：附加时正在放的那首，歌词若比音频短就配不上，下一首起正常；预取的文档轮到自己那首时若没有再出现
│     新副本，仍记在别的歌名下、配不上；当前歌没有自己的歌词时，其间出现新副本的别的文档（预取的下一首、
│     很晚才到的上一首）只要过得了上面的时长上限，就会被当前歌采用，并留在它名下；留存只在本次附加期间，
│     服务重启前播过的歌重启后再放，文档若没有出现新副本，仍按来历不明处理（真机见过：文档比曲目短 9 秒，
│     报了无歌词）；同名同歌手的两个版本时长相同时分不开，短版的文档还留在内存里时长版仍可能采用它
├─ 换歌时歌词已在内存（或留存里有）就同一次全扫配好再宣告；不在就先发空的 all_lyrics，头 3s 约每 0.4s、到 15s 约每 1.2s
│  找一次，找到即补发；15s 仍没有才发 index:-1（每首至多一次），之后退避到 60s 一次继续找
│  —— 自然播完切到下一首时歌词在开播后 0.3~0.5s 才到；审查方见过 10s 以上才到的
├─ TTML 用 encoding/xml 解析：Word 型的 <span> 为逐字；译文进 sub_text；roma_text 恒空
│  —— 时间写法：时钟值 [h:][m:]ss.mmm（冒号超过三段的拒绝），或不含冒号、带度量后缀 h / m / min / s / ms 的偏移值
│     （真机见过整份文档写成 begin="1.127s"）
│  —— 没有时间的 <span>（背景人声 ttm:role="x-bg"）当容器，内层逐字 span 各自成词；span 之间的空白并入前一个词；
│     行文本与译文里连续的 XML 空白折成一个空格，全角空格不折
│  —— 译文取 <text> 内全部文字（含内嵌 <span>）；多个 <translation> 时同一 itunes:key 先到先得，
│     第一种语言缺的 key 由后面的语言补上
│  —— 只有一行「纯音乐，请欣赏」的 TTML 按无歌词：all_lyrics 为空列表，index:-1 的 lyric_update 带这行文本
├─ 封面：随 song_info_update 的 cover_base64（data URI）发出，cover 恒为空串。宣告时还没有图的先不带图、到了补发；
│  换歌后存储里的图有时还是上一首的（约 0.4s 后才换）：与上一首那张相同而专辑不同时先不发，换了补发；
│  加载超时清屏后仍记着最近一次发出的图与专辑，清屏后的新歌照此比对
├─ 位置结构已确认、歌名歌词封面都已取到后，稳态播放零全扫
├─ 本地时钟：读数是整秒，跳到 N 的时刻真实位置已是 N+0.38~N+0.64（Apple Music 约每 256ms 才刷新一次位置）。
│  位置 = 锚点 + 墙钟流逝，读数每跳一次只把它夹回这个范围、在范围内不动；轮询下限 50ms；行号只往前走
│  —— 把读数 N 当位置 N、300ms 轮询时，歌词行平均晚 0.80s（新旧两版并排实测；新版 +0.05s）
├─ 已宣告、不在加载中、时钟在走时每 5 秒向服务端报一次位置采样（内部事件 position_sample，不外发）：读数走得比
│  墙钟慢时位置被夹回去而不发事件，无歌词的歌又没有别的带位置的事件，不报则服务端按墙钟外推的位置一直超前
│  —— 离线回放（时长 300s 的无歌词歌曲，读数每 1.5s 才前进一格、连续 40 格）：不报时 60s 后超前 20.00s，
│     报了之后段内最多超前 1.90s
├─ 位置停更 1.6s 判暂停；开播或播放中跳转确认后 8s 内放宽到 3s（startPauseThreshold / startWindow）
│  —— 新歌开头缓冲时位置会走一跳、停一两秒；跳转后的下一跳同样来得晚（真机拖动一次进度条，音频没断，
│     却在约 2s 后报了暂停）。代价是这 8s 里的真暂停最多晚 1.4s 发现
├─ 暂停中位置前进一跳（≤ 距上一轮读数的墙钟秒数 + 1.5s）先记下，2.5s + 一个轮询间隔内再来一跳才判恢复，
│  只发一次 playback_resume；代价是恢复晚报 1~2s
│  —— 只凭一跳会把暂停中往前拖一两秒当成恢复；门槛按墙钟算，轮询调慢（上限 2s）时恢复照样能判出
├─ 跳转要目标读数持续不短于 300ms（jumpHold）才认，期间任一次读数不指向它即作废——拖动进度条时读数会先闪一下
│  目标值又弹回，闪现持续到 Apple Music 下一次刷新位置为止（真机每 2ms 采样：10~14ms，或约 220ms）。
│  播放中读数偏出允许范围 >3s 是跳转，确认后发一次 playback_resume；暂停中其它位置变化算拖动，确认后只重锚、
│  推出目标位置的那一行歌词，不发 playback_resume
│  —— 代价是跳转在读数稳定约 0.3s 后才报，playback_resume 与目标位置的歌词行都晚这么多；门槛取 40ms 时，
│     闪现约 220ms 的拖动会连发三条 playback_resume、把原位置的歌词行又推一遍
│  —— 暂停中拖动一次可能先后推出目标与实际落点两处的歌词行：目标值的读数先停约 1.1s，之后才落到靠前 3~10s 处
└─ 进程退出（GetExitCodeProcess 判活）→ standby + process_exited，重新附加后重新发现位置结构（重启后地址变）
```

### 音频波形（WASAPI 进程级 loopback，全部播放器通用）

```
播放器进程树
├─ 目标进程名按播放器登记（procscan.PlayerProcess）；Apple Music 登记的是出声的 AMPLibraryAgent.exe 而非
│  AppleMusic.exe——前者不在后者的进程树内；applemusic.AudioProcessName 注释记录 2026-10-08 真机测得
│  AppleMusic.exe 树内帧在流动但 RMS 恒为 0
├─ 主进程：同名进程集合中父进程不在该集合内者（多个时取 PID 最小）
├─ 出声的可能是子进程（CEF / Chromium 系为 --type=utility 的音频服务进程；QQ 音乐另有异名子进程，同在捕获范围内）
└─ Windows 音频引擎：loopback 客户端以 48kHz / 2ch / float32 初始化，由引擎转换
   —— 独占 / ASIO 输出不经引擎，按机制应只得到零帧（未实测）

PlayerCap (audiocap 模块)
├─ 门控：无波形订阅时不扫描、不捕获（启动时清理遗留捕获子进程的一次进程枚举除外）；有订阅时捕获被 per-player 订阅的播放器，
│  根订阅下另捕获当前活跃播放器（含暂停中）与所有 playing 的播放器（切换时无需等激活）
├─ 进程发现：Toolhelp 快照选主进程，捕获前复核 PID 与进程名（防 PID 复用）
├─ 捕获子进程：同一 exe 以 --audio-capture-helper 启动，stdin 收控制命令、stdout 回传帧；
│  Job Object（KILL_ON_JOB_CLOSE）+ stdin 关闭即退出，主进程退出时随之结束
├─ 子进程内：ActivateAudioInterfaceAsync（PROCESS_LOOPBACK + INCLUDE_TARGET_PROCESS_TREE，
│  需 Windows 10 build 19041+）→ 降混前按声道取峰值 → 降混单声道 → RMS + 512 点幅度谱 → 可选音量归一化
│  → 按采样数分帧，每秒 audio-frame-rate 帧（默认 25）；无声时照发零帧保活，引擎无数据时约 100ms 一帧
├─ 故障隔离：单路无帧按播放器退避重试、连续 5 次失败放弃该播放器；子进程启动失败或自身崩溃后退避重启，累计 5 次启动失败或快速崩溃（期间稳定运行满 10 秒即清零）才全局放弃；
│  看门狗判子进程假死而重启时不退避、不计入崩溃次数；主进程侧异常只记日志，不影响歌词与特效
└─ 主进程按 magic 重对齐解帧，按 player 扇出到 /audio-ws（跟随活跃）与 /<player>/audio-ws
```
