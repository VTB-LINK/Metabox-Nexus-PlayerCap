## 尾换行缺陷

### 证据

- 酷我：`MUSIC_9.6.0.0_W1`，内嵌 Chrome 49。
- `libcef.dll` SHA256：`a98e2fcdcf66515dec05bcf6c9c92c3356f52b536e65f66ffda012ec15457514`。
- 历史 dump SHA256：`2e8750b07b41abfdc10fbd31156460f9780011c7142e082c6ef1201ff5c999e7`。
- dump 与磁盘 PE 的大小、时间戳、校验值一致，故障处字节也一致。
- dump 中 `EDI=0`，故障在 `libcef+0xA5DA88` 的 `mov eax,[edi]`；访问的是协议 JSON 解析结果。
  后续才读取 `id` 和 `method`，尚未执行 `Runtime.evaluate` 或原生桥调用，因此不支持“桥返回序列化导致此处崩溃”的旧假设。
- 8/16 位解析器在 RVA `0x7E0932` / `0x7E09AB` 要求 `tokenEnd == end`，不满足即返回空。
  独立复核还追踪了 `}` tokenizer 到 `0x7E167D`：末指针停在 `}` 后，没有吞掉尾空白；对象解析路径原样返回该指针。
- 真实 Gorilla WebSocket 帧离线捕获：`WriteJSON` 发送 124 字节，紧凑消息是 123 字节，唯一差异为末尾 `0A`。
  这是旧解析器拒绝的形状，且 dispatcher 对空结果没有 release 模式检查。

这些是本地 dump / 二进制 / 实际帧的证据。REA native provider 在本机不可用，离线分析使用现成 Capstone 与显式 PE/minidump 解析；未修改或执行酷我 DLL。
原始分析使用本机临时产物，未随仓库保存；上述哈希、位置和方法是可用证据摘要，不要求读者访问该机器。

### 修复与限制

发送端改为 `json.Marshal` + `WriteMessage(TextMessage, payload)`，保证紧凑对象、无尾换行。
保留已经真机验证的 `JSON.stringify` 桥返回边界，但不再将它当成历史崩溃原因。
`framing_test.go` 捕获真实新旧 writer 帧，并仅模拟二进制已观测到的末指针判据；它没有执行 libcef。
`transport_test.go` 直接检查生产发送帧，隔离副本重新加尾换行后确实失败。

历史 dump 缺少请求字符串所在堆页，不能把离线重建的消息说成事故抓包；空输入或其他无效协议也可能进入同一空指针路径。
因此结论是**静态分析得到与现场吻合的致崩路径，发送端已规避该形状，未动态复现**；没有故意向真实播放器重放致崩帧，历史事故因果未被证明。

### Race 编译环境与复跑

2026-10-23：Go `go1.26.5 windows/amd64`，WinLibs GCC `16.2.0`（POSIX / SEH / UCRT，MinGW-w64 `14.0.0`，r2）。
WinGet 源报 `0x80071130`，刷新后仍失败，改用对应 GitHub release 的便携包；解压前 SHA256 校验为
`d5dbafc4a170e762ca6143151ec918fb9e2c72736fb14cd704abebc6bdd5276a`。
将便携包安装到自行选择的目录，把其中 `mingw64\bin` 加入当前终端 PATH；不要求固定用户名或路径。
`gcc --print-file-name libsynchronization.a` 返回存在的完整库路径，加入 PATH 后 `go env CGO_ENABLED` 自动为 `1`。

当前已打开的终端可能仍持有旧 PATH，可显式设置后复跑：

```powershell

$env:CGO_ENABLED = '1'
Remove-Item Env:PLAYERCAP_LIVE,Env:PLAYERCAP_KUWO_PIPELINE_LIVE -ErrorAction SilentlyContinue
go test -race ./... -count=1
```

本次全仓命令退出码为 `0`；原始日志仅在本机保留、不是仓库夹具，可按上述命令重新执行。
未检测到数据竞争或测试失败，因此没有为此修改业务代码。这里的通过仅覆盖实际运行的离线测试路径，

## 运行边界

- 切换《梦的光点》到《光辉岁月》期间一次快照不符合已验证协议，服务先清空旧状态，约 3 秒重连后恢复。
  保留 fail-closed：未经原始过渡值验证，不把未知状态猜成 playing，也不为掩盖间隙继续显示旧歌曲。
  （2026-10-24 补：在 `9.6.0.0_UG1` 上复测，这不是偶发而是每次切歌必现；原始过渡值已取得，见“构建匹配与真机复测”，现已改为重试。）
- Seek 后底层核心短时多次调整位置，会产生连续几拍位置校正；不是同一拍重复发 resume。
- 读取准入对 `9.6.0.0` 的任意渠道后缀放行：桥版本与所选页面目录的后缀须一致，PlayerCore 按结构匹配（解析导出表定位单例、读位置函数须是该单例虚表的虚方法）加原生音频后端，不再比时间戳。EXE 哈希只用于受控重启前的白名单校验（当前 `w1`、`ug1`），已就绪桥不校验 EXE 哈希；白名单外的构建不自动重启。读取准入与重启白名单是两回事。
- 翻译支持实测 `[ml:1.0]` 双语 lrcx（见 [协议 §7](kuwo-lyric-protocol.md#7-2026-10-24双语翻译)），音译、其他数字版本未提供。评论者报告的 `9.3.9.0_BD1` 不在支持范围。`9.6.0.0_W1` 由 PR 作者的测试用户称经酷我客户端升级弹窗获得（作者自述）；2026-10-24 另一台机器上的酷我目录由 `9.3.9.0_BD1` 变为 `9.6.0.0_UG1`（相对 W1 只有渠道后缀不同；推测为客户端自升级，未核实升级方式）。两个后缀的独立安装包链接均未核实，也不保证该升级对所有用户可用或给出同一后缀。
- 音频 RMS 按用户要求不作为本次阻塞项；客户端画面逐字高亮及声卡/OBS 输出延迟未做同步校准。
- 无长期 soak、强杀渲染器、全部缓冲状态或所有进程生命周期的穷举测试。
- 上述 18765 短跑测试结束时服务与订阅均已退出；这只描述该次测试，不承诺开发机此后没有其他测试服务。

## 构建匹配与真机复测

设计见 [构建匹配设计](kuwo-build-matching-design.md)。实现后的独立审查与真机复测补出下列几项，均已修复并补回归：

- **歌词响应编码是 GB18030，不是 GBK**（真机韩语歌《Whiplash》，2026-10-24）。同一份响应含 305 个四字节序列：按 GBK 解码得到 394 个替换字符（标题成了 `aespa (�2�3�2�1…`），按 GB18030 解码为 0 个、标题为 `aespa (에스파)`。GB18030 是 GBK 的超集，中文歌词解码结果不变。请求一侧的 GBK 编码（歌名与歌手）不动：不可编码的可选字段仍省略，RID 足够取词。
- **每次切歌的约 3 秒空窗**（`9.6.0.0_UG1`，2026-10-24，6 次整曲切换 6 次全中）。原始响应已抓取：切歌那一瞬间，`GetPlayStatus` 前后两次都返回空字符串，而 `GetNowplaySong` 已是新歌；5 次抓取的空窗持续 207、490、453、490、498 毫秒。原实现把它当作 `ErrUnavailable`（协议违规），`runSession` 只容忍 `ErrSongChanged`，于是会话结束、状态变 `waiting_process`、3 秒后重连。现在 `parseSnapshot` 把空状态按“状态变化中”（`ErrSongChanged`）处理，会话在 1 秒内重试；非空但格式错误的状态（空白、缺键、重复键、非法 RID）仍是 `ErrUnavailable`，保持 fail-closed。快照瞬态与核心样本对账改用两个独立的 1 秒预算，避免前者吃掉后者。修复后复测（21:39 起，用户按“没听过的歌”操作，未单独核验这些歌没有本地缓存）：5 首歌之间的 4 次切换，各出现一次“状态变化中”，持续 399、443、384、507 毫秒后恢复，全程没有 `session ended`，也没有 `waiting_process`；新歌的事件在恢复的同一时刻发出。**取舍（有意的，与上文“运行边界”里的原则不同）**：重试期间旧歌的公开状态不清除，旧歌最多多显示到新歌到来，实测约 0.4 到 0.5 秒，之后被新歌直接替换而没有空白；预算按轮询检查，不是严格期限：最坏情况下快照瞬态与核心对账各用满 1 秒，两种失败交错时还可能再多出最后一个不足 1 秒的瞬态窗口（快照成功会重置快照预算），量级约 3 秒；实测每次只有 0.4 到 0.5 秒。若稳定超过预算，仍然降级重连并清空。选择保留而不是在首次失去歌曲身份时清空，是因为后者会让每次切歌多出一段空白闪动。
- **活性校验的累计时间**：从暂停进入播放的首个采样，其与上一个（暂停）采样之间的间隔不是播放时间，不计入。慢轮询（最长 2000ms）下原写法会把这段间隔记入，使触发提前一拍。
- **重启白名单的路径**：`filepath.Clean` 会在字面上折叠 `..`，使只是折叠后才合法的路径通过。现在含 `..` 分量的路径直接拒绝（重启资格本来还要哈希匹配，所以这不是未知哈希放行）。
