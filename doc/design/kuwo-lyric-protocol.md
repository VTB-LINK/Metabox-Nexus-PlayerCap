# 酷我歌词协议（已逆出并实现）

本文是**协议真源**：酷我 9.6.0.0 的歌词请求/响应格式，以及它是怎么被逆出来的（证据链）。
实现见 `player/kuwo/lyric/`，夹具与真机用例都在那里。

状态：**请求与响应两侧都实测通过**；我们用自己拼的请求取到了任意歌曲的歌词，不依赖客户端。
未决部分见 §5。

---

## 1. 协议

### 1.1 请求

```
GET http://newlyric.kuwo.cn/newlyric.lrc?<query>            (明文 HTTP)

query = base64( xorCycle(plain) )
plain = "user=<uid>,<version>,<exe>,KwMusic"
        "&requester=localhost&req=1 "                        ← 注意 1 后面那个空格，客户端原样带
        "&songname=<歌名 GBK>&artist=<歌手 GBK>"
        "&rid=MUSIC_<纯数字 id>&lrcx=1&olrc=1"

xorCycle(b)[i] = b[i] XOR "yeelion"[i % 7]                   ← 酷我内部代号，7 字节，循环
```

- **不需要签名**。客户端明文里没有 `sig`，服务端也不校验（实测直接用 `rid` 就能取到）。
- `uid` 未登录写 `0` 也能取到（实测）。
- `version` / `exe` 是客户端自称；实测不影响结果，实现里照抄 `MUSIC_9.6.0.0_W1` /
  `kwmusic_web_1.exe` 以免服务端以后按版本分流。
- 歌名/歌手以 **GBK** 字节进明文（不是 UTF-8，也不是 URL 转义）。

### 1.2 响应

```
<header 若干行, CRLF 分隔>  CRLF CRLF  <zlib 流>

zlib 解开 = base64 文本
base64 解开 = xorCycle(LRC 原文)
LRC 原文 = GB18030 编码（GBK 的超集；韩文音节、生僻字、emoji 是四字节序列，按 GBK 解码会变成乱码，2026-10-24 在韩语歌上实测）
```

`header` 是 `key=value` 逐行，实测字段：

| 字段 | 示例 | 说明 |
|---|---|---|
| `tp` | `content` | `content` 表示下面有歌词正文 |
| `path` | `1647836915` | 内部路径 id |
| `score` | `5` | 匹配评分 |
| `provider` | `a` | 提供方 |
| `lrc_length` | `5260` | **base64 文本**的长度（不是最终 LRC 的长度） |
| `cand_lrc_count` | `0` | 候选歌词数 |
| `lrcx` | `1` | 新格式标志 |
| `show` | `1` | —— |

### 1.3 LRC 格式

```
[kuwo:065]
[ver:v1.0]
[ti:湮灭]
[ar:萨吉]
[al:湮灭]
[by:kalakaer1]
[offset:0]
[00:00.000]<153,-153>湮<408,102>灭 <663,357>(《<918,612>玉...
[00:00.816]<153,-153>词：<408,102>赵<663,357>瑟
```

- 行时间 `[mm:ss.xxx]`；`[offset:±ms]` 是整体偏移，要累加到每一行。
- 标签行 `[kuwo:]` `[ver:]` `[ti:]` `[ar:]` `[al:]` `[by:]` 不是歌词。
- 行内的 `<a,b>` 是**逐字标记，带时间信息**（不是像素坐标——这一点有决定性证据，见下）。

#### 逐字标记 `<a,b>`：精确换算已恢复（2026-10-23）

**决定性证据是客户端的解析与时间计算指令**，不是仅凭重复文字的数字不同。
重复行差异只能作为线索（排版也可能受上下文影响）。早期《你的背包》
（rid 491280316）的重复行记录保留如下：

| 重复行 | 第一次出现的标记 | 第二次出现的标记 |
|---|---|---|
| 你的背包 对我沉重的审判 | `<3728,-3728> <6692,-1100> <13094,-1658>` | `<3448,-3448> <6626,-1454> <13176,-1944>` |
| 借了东西为什么不还 | `<3912,-3912> <7326,-1458> <10196,2260>` | `<5648,-5648> <7700,772> <10794,2874>` |
| 终有一天陪着我腐烂 | `<5512,-5512> <6846,1422> <8992,3344>` | `<4968,-4968> <7558,-106> <8632,4568>` |

对本轮实测的正常头，先把 `[kuwo:H]` 中的 H 按**八进制**读成整数 N，再按十进制拆成两个系数：

```text
C1 = N / 10              // 整数除法
C2 = N % 10
startMs = (a + b) / (2 * C1)
durationMs = (a - b) / (2 * C2)
endMs = startMs + durationMs
```

这些是**相对行首的毫秒**；绝对位置再加行基准时间。两个除法分别执行，客户端为有符号
`idiv`（向零截断）。系数必须按每份歌词读取，不能固定成 6，也不能把 a 或 b 直接当开始/结束。
对应编码关系是 `a=C1*start+C2*duration`、`b=C1*start-C2*duration`。

| 歌词头 | N（十进制） | C1 / C2 | 开始 / 时长的除数 |
|---|---:|---|---|
| `065` | 53 | 5 / 3 | 10 / 6 |
| `067` | 55 | 5 / 5 | 10 / 10 |
| `104` | 68 | 6 / 8 | 12 / 16 |
| `0115` | 77 | 7 / 7 | 14 / 14 |
| `126` | 86 | 8 / 6 | 16 / 12 |

例如 `065` 的 `<153,-153>` 为开始 0ms、时长 51ms；`<408,102>` 为开始 51ms、时长 51ms。
`104` 的 `<4000,-4000>` 为 0–500ms，后一个 `<3256,2744>` 为 500–532ms：
**a 从 4000 降到 3256，实际时间却前进**，直接用 a/6 会出错。

一个标记管辖它后面到下个标记前的**文本片段**，不保证恰好一个汉字；应保留空格、标点与多字符片段。
真实样本存在零时长、间隙和 1ms 微重叠，不能用“下一个字开始”代替当前字的独立结束时间。
没有标记的纯 LRC 仍需逐行降级。

纠正旧样本判断：《湮灭》片头信息有均匀的 51ms 片段，但 8.934s 正文行的时长为
862、428、253、1240、272、420ms，并非整首都是均匀铺开的时间。

2026-10-23 接入更新：`ParseLRC` 已返回行时间和 `Words`（开始、时长、文本），适配层已输出 `text_detailed`。
无效头或无效字级标记整行降级；负文件 offset、零时长、空格及多字符片段均有回归测试。
客户端静态证据、样本覆盖与剩余边界见 §6。原 `TestLiveWordMarksCarryTime` 只检查特定样本的
重复行差异，不能证明换算公式，也不能在只修改注释/文档时自动报错。

## 2. 证据链（怎么反出来的，供复查）

按实际顺序，每步都留下可复算的依据：

1. **抓请求**：扫 `kwmusic.exe` 的私有可读写内存，找 `http://newlyric.kuwo.cn/newlyric.lrc?`，
   得到 `?<base64 blob>`。同一次抓到的两条请求（不同歌）有 **49 字节公共前缀** ⇒ 位置固定的
   密钥流、无链接式反馈（否则公共前缀不可能保留）。手拼 `?rid=…` 一律返回
   `TP=ERROR REQUEST`，说明服务端只吃这套编码。
2. **重放**：把抓到的 URL 原样重放 → `HTTP 200`，响应 = 文本头 + 空行 + zlib；zlib 解出的
   是 8288 字节 base64 文本，再 base64 解开仍是二进制（6214 字节）⇒ 还有一层异或。
   实测重放**不依赖时间**，同一 URL 隔一小时后重放仍返回同一份内容。
3. **拿明文**：客户端自己解好的 LRC 就在 `kwmusic.exe` 内存里（ASCII，`[kuwo:…` 开头）。
   同一首歌的响应密文 7290 字节、内存明文也正好 7290 字节 ⇒ 逐字节异或得到 7290 字节密钥流。
4. **看密钥**：密钥流前几字节是 `79 65 65 6C 69 6F 6E 79 65 65 …` = ASCII **`yeelion`** 的
   循环，**周期 7**（`yeelion` 是酷我早期内部代号；`KwModLyric.dll` 里也能搜到该串）。
   用周期 8 去测会漏掉——这是排查时踩过的坑。
5. **跨歌验证**：用这把钥匙解**另一首歌**的响应 → 完整 LRC，中文（`[by:天琴实验室AI生成v1.0]`）
   完全正确 ⇒ 密钥固定、与歌曲无关、与长度无关。
6. **反推请求**：同一把钥匙解抓到的请求 blob → 明文
   `user=…&requester=localhost&req=1 &songname=…&artist=…&rid=MUSIC_…&lrcx=1&olrc=1`
   ⇒ 请求与响应**共用同一把钥匙**，且没有签名字段。
7. **自己造请求**：按该明文拼 `rid=MUSIC_658118183`（湮灭/萨吉）→ 服务端返回 `[ti:湮灭]`，
   35 行、行时间与逐字坐标都在。至此整条链闭环。

### 红鲱鱼：`KwLib.dll` 的 `Entrypt::Encrypt`

`KwLib.dll` 导出 `Entrypt::Encrypt(char*,int,int)` / `Decrypt`，看着就像"就是这个"，**但不是**：
它是「按 `133 % len` 右移 + 用 `KoOtOiTvINGwd` 循环异或 + 按 `71 % len` 左移 + 用
`_Y8g2E6n0E1i7L5t2IoOoNk` 循环异或」两轮变换（三个参数里第三个是开关，非 0 直接 no-op）。
把它套到抓到的歌词请求/响应上都解不出明文——歌词通道根本不经过它。
（该函数的结构已完整反出并可与它的导出互为 oracle 验证，但本项目用不上，故不实现。）

## 3. 实现

`player/kuwo/lyric`：

| 符号 | 作用 |
|---|---|
| `Request{Version,UID,Song,Artist,RID}` + `PlainBytes()` | 拼明文**字节**（歌名/歌手是 GBK，故返回 `[]byte` 而非 `string`） |
| `EncodeQuery([]byte) string` / `DecodeQuery(string) ([]byte,error)` | XOR `yeelion` + base64 / 逆运算 |
| `Client.Fetch(ctx, Request) (Response, error)` | 发请求、解四层（头 / zlib / base64 / 异或+GB18030） |
| `DecodeResponse([]byte) (Response, error)` | 纯函数版解码，便于离线测试 |
| `ParseLRC(string) []Line` | 行时间 + 去掉 `<x,y>` + 并入 `[offset:]`，跳过标签行 |

夹具（都来自实测，不是编的）：

- `testdata/client_query.txt`：`plain_gbk_b64=`（客户端加密前的明文，GBK 字节）+
  `query=`（它自己拼进 URL 的 base64）。**逐字节比对**，把「XOR `yeelion` + base64」钉死。
- `testdata/resp_xiangni.b64`：真实响应体（文本头 + zlib + base64 + GB18030 四层齐全）。

用例：离线四个（编码指纹、解码链、解析、错误路径）+ 真机一个
（`PLAYERCAP_LIVE=1 go test ./player/kuwo/lyric -run TestFetchLive -v`，走公网，不进 CI）。

## 5. 覆盖度与未决

**能拿到**：整首 LRC、行时间、`[ti:]/[ar:]/[al:]/[by:]/[offset:]`、**逐字标记 `<a,b>`**
（精确时间换算见 §1.3）、部分歌还有 `[total:<毫秒>]`（实测《晴天》）。

**拿不到 / 未决**：

1. **逐字输出已实现，画面同步未校准**：精确语义已恢复并经五份样本交叉核对（§6），头系数、片段开始/时长、
   `text_detailed` 映射与降级回归均已实现；完整管线实测《梦的光点》474 片段、《光辉岁月》349 片段。
   客户端画面高亮及声卡/OBS 延迟的联合对照仍未进行。
   纯 LRC 不应伪造逐字；正文不能因片头署名采用均匀时长而被判为没有真实逐字。
2. **翻译 / 音译**：2026-10-24 已取得并接入 `[ml:1.0]` 双语 lrcx 的平台译文（§7）；音译与其他双语格式未验证。
3. **时长**：响应头与 LRC 一般没有时长（`[total:]` 只在部分歌里出现）；`GetNowplaySong`（CDP 桥）也不带。
   逐字/行时间之外要时长，走 `player/kuwo/pos` 的内存结构或 `act.log` 的 `DUR:<秒>`。
4. **没有歌词的歌**：响应 `tp=none` + **零载荷**（实测 4 首都是 68 字节头、0 字节正文）。
   库返回 `ErrNoLyrics`，调用方当"没有"处理、别重试。
5. **失效风险**：协议未公开，酷我改版本可能整体换掉。固定夹具只能检查实现对已保存数据的兼容性，
   不能探测线上变化；服务端是否变化需要显式运行联网用例。
6. **请求频率**：换歌各取一次即可（一首歌的歌词是静态的），不要放进轮询循环。

## 6. 2026-10-23 逐字时间研究证据

### 6.1 客户端静态证据

目标：测试版安装目录中的 `bin/KwModLyric.dll`，x86。
SHA-256：`31fbaef763896a7e299ed165b37e051afb37b3d77f27d5ff1187f9f45bbdcdb7`。
REA `open_binary` 核对文件身份；下述指令来自本机 Python/Capstone 对文件字节的离线反汇编，
不是 REA 反编译器输出，也不是运行时观察。没有加载执行 DLL、写进程内存或控制播放器。
以下均为 RVA（本文件首选基址 `0x10000000`）：

| 位置 | 观察 |
|---|---|
| `0xF389` | 引用 `kuwo:`，随后处理头值 |
| `0x10BF0–0x10C50` | 头值解码循环：`acc=(acc<<3) OR digit`；正常 0–7 数字等同八进制 |
| `0xF47C–0xF4B1` | 调用头值解码，再 `idiv 10`，商/余数分别写对象 `+0x294/+0x298` |
| `0xFD05–0xFF73` | 搜索 `<`、`>`、`,`，分离两个数，以及本标记后至下一标记前的文本 |
| `0x1009E–0x1012E` | 保存片段文字位置；两个数转换后存入记录 `+4/+8` |
| `0x10699–0x106F3` | 末行结束时间：按上述两系数计算 `(a+b)/(2*C1)`、`(a-b)/(2*C2)`，相加 |
| `0x10737–0x1075D` | 相对结束时间再加该行时间，生成最后一行的结束时间 |
| `0x16491–0x164E0` | 实时歌词路径再次执行同一开始/结束公式；两个除法均为 signed `idiv` |
| `0x1663B–0x1664A` | 计算结果存入当前字开始 `+0x44`、结束 `+0x48` |
| `0x167A7–0x167D9` | 将这两个字段传给 `iWordStart:%d iWordEnd:%d` 日志格式串 |

旧记录称调试字符串无 xref，本轮在 `0x167C4` 找到了明确的 `push 0x1001C908`。
代码夹有双条件跳转与 call/pop/ret 干扰字节，直接从任意地址线性反汇编会错位；上表位置按真实
分支目标解码。复查时不要把跳过的垃圾字节当成时间计算代码。

客户端头解码对数字 8 也有宽松接受路径，缺失/零系数另有 legacy 分支；本轮正常样本未覆盖这些输入。
新解析器应对不支持的头明确降级，而不是复制未验证的兼容分支或猜一个系数。

## 7. 2026-10-24：双语翻译

本机播放《アイロニ - 4円》（RID `7051483`）时，同一歌词请求的解码内容带 `[ml:1.0]`、
`[kuwo:054]`。无需额外请求：译文以 `<0,0>` 标记插在原文之后，时间戳却等于**下一物理行**的时间。
末行译文之后还有空的时间戳行，不能在配对之前丢掉。

以下是保留结构、替换正文后的合成示例（不是歌曲原词）：

```text
[ml:1.0]
[kuwo:054]
[00:01.000]<400,-400>original one
[00:02.000]<0,0>translation one
[00:02.000]<800,-800>original two
[00:03.000]<0,0>translation two
[00:03.000]
```

客户端 `bin/html/webdata/netsong/static/singleComment.js` 的 `handleSetCurLyric` 在 `IsMulti=1`
时比较当前行和下一行时间，相等就将当前文本附到上一行；`ShowMulti` 只控制显示。
`[ml:1.0]` 与该桥标志的直接原生映射尚未追踪，因此本实现保守限制在上述实测格式：
有效逐字头、精确零标记、相邻原文、下一物理行同时间戳，且译文时间晚于原文。
未知/冲突头或异常配对保留为逐行歌词，不根据字符语言或最近时间猜配。

译文写入原文的 `sub_text`，不占独立原文行、不改原文逐字时间。当前样本解析出 75 行、
72 行非空译文、757 个原文片段，含末行翻译；空白占位不产生译文。音译、纯行双语变体及其他
`ml` 版本未验证。本功能提供平台译文，不调用机器翻译。
