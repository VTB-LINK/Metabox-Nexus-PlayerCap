# config 版本字段与 offset 延迟语义设计

本文覆盖里程碑 4.0 合并处理的两项改动，二者都落在 `config/config.go` 与 `main.go` 的启动路径上：

- issue #54：与时间有关的 offset 一律按延迟处理，正值 = 延后，负值 = 提前。
- issue #32：config.yml 带版本字段；程序更新后改写该字段，跨过语义变更时自动迁移；网关可要求把旧文件留作备份后按模板重建。

已定的前提（#54、#32 的评论，2026-10-09）：没有版本字段的 config.yml 一律视为 v3；版本字段取值跟随程序版本，小版本也跟；程序更新后该字段改写为新版本，其余内容不变；自动迁移与强制删除重建都做；强制重建不询问用户，按门槛判定（配置低于网关字段给出的版本即重建）。

状态：已实施。文中「现状」指实施之前，均对 `ce1f934` 读代码核实；标「推断」的未实测。规矩与守卫状况以 `AGENTS.md` §3.2、§3.3、§3.5、§4 为准。

实现与本文的出入：

- §3.2 插入版本键的位置：不是「第一个既非空行也非注释的行之前」，而是该行及紧贴其上的注释之前，原先写给第一个键的注释仍贴着它；缩进跟随该行。
- §3.2 版本键的值写在下一行、或写成块标量时，键行本身被认作一行并替换，由改写后的校验拦下，而不是由「找不到认得的版本键行」拦下；结果同为不写文件。
- §4.2 整数键行另有两条要求：冒号之后须有空白；行里的数字须等于解析出的原值（`offset: 010` 解析为 8，不写文件）。
- §3.3 把「文件只读」列为写入失败，而 §3.6 的改名对只读文件照样成功（Windows 上实测），所以改写之前另加显式检查：只读的 `config.yml` 不改写。强制重建不做这项检查。
- §3.6 没有写到的一处：放置因「已存在」以外的原因失败时，迁移与只改版本键两路把备份放回 `config.yml`（同样是不存在才放置），放不回时原文件留在备份名下；强制重建不放回。
- §5.3 版本键非法的文件按「文件版本未知」处理，不判定、不重建。
- §3.1 第 4 步的 UTF-8 检查在整套流程里是重复把关：UTF-16 的文件另被「恰好对应一行」与校验拦下，去掉该检查只有针对它本身的用例变红。文档数量的检查不是：第二个文档里被注释掉的键只有它拦得住。
- §8 第一条不再适用：issue #61 已先合入，新增文案在调用点写英文原文，中文在译表里。

## 1. offset 改为延迟语义（#54）

### 1.1 现状与算式

offset 现在是「提前量」（模板注释：正值=歌词提前）。它只经两类算式生效，其余位置都是原样传递：

| 算式 | 位置 | 现在 | 改后 |
|---|---|---|---|
| 行与逐字的播出时间 | `player/player.go` 的 `AdjustLyricPlayTime`（`LyricPlayTime`、`BuildLyricLine`、`BuildLyricUpdate`、各家 `applyDetailedOffset`、cloudmusic 的 `applyTextDetailedOffset` / `ParseYRC` 都经它） | `max(0, t - offset)` | `max(0, t + offset)` |
| 歌词行匹配用的时刻 | 六家各写一处：wesing `pollLyrics` 的 `adjustedTime`，cloudmusic `runSession` 的 `currentTime`，qqmusic、kugou、sodamusic 轮询循环的 `matchTime`，applemusic `session.emitLyricLine` 的 `interp+s.offsetSec` | `位置 + offset` | `位置 - offset` |

第二类六处收拢为 `player/player.go` 的一个函数（暂名 `LyricMatchTime(position, offsetSec)`），符号从此只在该文件的两个函数里。理由：六处里只有 applemusic 有离线会话测试，其余五家漏改一处不会红，表现为该播放器 `lyric_update` 的发出时刻与其 `play_time` 相差两倍 offset。

### 1.2 新默认值（旧值取反，观感不变）

| 键 | 现值 | 新值 | 出处 |
|---|---|---|---|
| `offset` | 200 | -200 | `DefaultConfig()` 与模板 `defaultConfigContent`，两处同改 |
| `cloudmusicv3-offset` / `qqmusic-offset` / `kugou-offset` / `sodamusic-offset` / `applemusic-offset` | 500 / 400 / 430 / 340 / 400 | -500 / -400 / -430 / -340 / -400 | 只在模板 |
| `# wesing-offset: 0` | 0 | 0 | 模板的注释示例 |

`DefaultConfig().Players` 仍为空 map：模板里写了覆盖值而内置默认回退全局值的差异（AGENTS.md §5.2「陷阱三」）不在本项内消除，见 §4.6 与 §8。

### 1.3 对外事件字段：数值不变

设旧值为 `A`、新值为 `D = -A`，逐个算式核对：

- `timestamp`：歌词时间轴原值，不含 offset，不变。
- `play_time`（行、`text_detailed.play_time`、`words[].play_time`）：`max(0, t - A)` 变为 `max(0, t + D)`。IEEE 754 的减法即加上相反数，`float32(-A)/1000` 是 `float32(A)/1000` 的精确相反数，结果逐位相同，含钳到 0 的情形。
- `lyric_update` 的发出时刻与 `index`：判据 `位置 + A >= 行时刻` 变为 `位置 - D >= 行时刻`，同上逐位相同。
- `position`、`progress`、`duration`（`lyric_update`、`all_lyrics`、`playback_pause` / `playback_resume`、内部的 `position_sample`）：六家传入的都是未加 offset 的实时位置（kugou、sodamusic 的 `interpSec`，qqmusic 的 `progressSec`，cloudmusic 的 `clock.GetCurrent()`，wesing 的 `playTime`，applemusic 的 `clk.live`），与 offset 无关，不变。服务端的外推（`PlayerState.livePosition`）不读 offset。

结论：同一份歌词、同一观感下，各事件的字节不变；变的只有配置的写法与回显。

### 1.4 配置回显与横幅

- `/service-status` 的 `config`、`config_effective` 里 `offset` 与六个 `<player>-offset` 由正变负，类型仍是整数，键名与 `config_overwritten` 不变；`buildConfigEcho` 不必改。
- 对客户端的影响：只把这些键当展示用的不受影响；拿它自行换算时间的（例如由 `timestamp` 推 `play_time`）方向会反。仓库内的 `lyric_page.html`、`effect_page.html` 不读 `/service-status` 的配置（全文检索无引用）。前端仓库是否读取未核实，实现合入前须通知。
- 对客户端的建议：不要拿回显的 offset 自行换算时间，直接用事件里的 `play_time`；它在两种语义下取值相同（§1.3），客户端因此不必知道后端是哪一种。
- 确需区分时，只靠 `version` 做不到：发布版本的分界与迁移边界相同，是 `4.0.0-0` 而不是 `4.0.0`（`4.0.0-beta.N` 已是延迟语义）；开发构建的 `version` 是 `0.0.0` 或非 semver 串，从字符串上分不出。可行的做法是在 `/service-status` 现有的 `capabilities`（`server/server.go` 的 `capabilities`，现只有 `init_position_live`，供前端按项探测后端行为）里加一项，有它即延迟语义，对预发布与开发构建同样成立。代价是一个字符串、`server/capabilities_test.go` 的期望值与两份文档里的说明。已定（2026-10-09）不加，理由见 §8。
- 启动横幅逐键取自同一份回显，自动显示为 `offset=-200ms`，`bannerGlobalLines` 的行标题「全局偏移与轮询」不改。
- 遥测上报的配置（`telemetry/appinfo.go`）里 offset 同样变号，跨版本比较时须知。

### 1.5 要改的位置

- 代码：§1.1 两类算式；`DefaultConfig()`；模板的取值与注释（「歌词延迟（毫秒），正值=延后，负值=提前」）；`Load()` 里 `-offset` 与 `-<player>-offset` 的帮助文案及其在 `i18n/messages.go` 的两条译文；`player/player.go`、六家播放器与 `tools/docsample/main.go` 里写着 `- offset` 的注释。
- 命令行：负值写作 `-offset -200` 或 `-offset=-200`。`flag` 包对非布尔参数取下一个实参为值，前导 `-` 不影响（读标准库源码得出，未实测；实现阶段经真实 `Load()` 加用例）。
- 测试：`player/lyricplaytime_test.go` 里以「减 offset」为期望的用例按新语义改；`bannerconfig_test.go`、`configecho_test.go`、`config/templatedefaults_test.go` 等以默认值 200、500 为期望的用例随默认值改。
- 文档与仓库根 `config.yml`（模板的一份副本，已入库）：清单见 §7。

### 1.6 其它带 offset 字样的量

逐处过了全仓的 `offset` / 「偏移」，以下与本项无关，不改：LRC / KRC 的 `[offset:]` 标签（`player/krc` 丢弃它，符号约定未验证）；applemusic 的 `flipLagMin` / `flipLagMax` / `seekLag`（读数滞后的测量值，不是用户配置）；qqmusic 的 `dllOffsets`、kugou 的 `patchEntry.offset`、音频帧头的字节偏移、页面脚本里的 `offsetWidth`。与时间有关的用户可配 offset 只有 `offset` 与 `<player>-offset` 两种键。

## 2. 版本字段

### 2.1 键名与归属

键名 `config-version`，顶层键，模板里放在文件头注释之后、`addr` 之前，带一行注释说明它由程序维护。理由：与现有键同为连字符小写；带 `config-` 前缀，读者不会把它当成「要运行哪个版本的程序」。

它不是配置项：没有命令行参数，不经 `mergeYAML`，不进 `/service-status` 的配置三件套（三件套的键集合与类型是对外约定），不进 README 的命令行参数表。它只出现在模板一处，须在 `config/keyplaces_test.go` 里登记为具名例外（现无例外，AGENTS.md §3.3 已预留这一做法）。对用户的呈现只有启动横幅的配置文件行（§3.5）。

### 2.2 取值与读取

- 写入的规范形式带 `v`（已定，2026-10-09），即 `normalizeSemver(Version)` 的结果：保留预发布后缀，加双引号，如 `"v4.0.0"`、`"v4.0.0-beta.3"`。与 `tag_name`、`config_force_update` 的写法一致。加引号是为了手改时不被 YAML 解析成别的类型。
- 读取时带不带 `v` 都认，并容忍有无引号、大写 `V` 与首尾空白，规范化方式同 `main.go` 的 `normalizeSemver`，合法性用 `semver.IsValid` 判。读到不带 `v` 的合法版本号不算非法，下次改写版本键时顺带写成规范形式。这段逻辑放在 `config` 包内；`golang.org/x/mod/semver` 是纯 Go，不破坏 `GOOS=linux` 构建（AGENTS.md §0 第 3 条）。
- 没有该键：视为 `v3.0.0`，对用户写作 v3。
- 键存在但不是合法版本号（写成数字、空串、任意文字）：视为已由 4.0 以上的程序处理过，不迁移，把该键改写为程序的盖章值并告警。理由：3.x 及更早的程序从不写这个键，键存在说明文件经过新程序或人手；此时按 v3 再迁一遍会把已取反的 offset 再取反，而且没有任何报错。

### 2.3 比较

按完整 semver 比较（`semver.Compare`），预发布低于同号正式版。迁移步骤的边界（§4.1）取「首个含该变更的版本」；拿不准时取该版本号的最低预发布 `X.Y.Z-0`。本次为 `4.0.0-0`：4.0.0 的任何预发布与正式版都不低于它。若写成 `4.0.0`，由 `4.0.0-beta.3` 盖过版本号的文件下次启动仍低于边界，会再迁一遍。

### 2.4 盖章值与开发构建

「盖章值」是程序写进 `config-version` 的值：

- 发布版本（`isReleaseVersion(Version)` 为真）：`Version` 的规范形式。
- 开发构建（本地构建的 `0.0.0`，或 CI 开发构建的非 semver 版本号）：代码里最新一步迁移的边界，现写作 `"v4.0.0-0"`。

开发构建不能照写 `0.0.0`：它低于任何边界，下次启动会把已迁移的文件再迁一遍。写边界的含义是「到这一步为止的迁移已做」：之后由发布版本读到时，`4.0.0-0` 低于任何 4.0.0 的预发布与正式版，照常改写为发布版本号且不再迁移；由含更新迁移步骤的构建读到时，照常执行新步骤。

设文件版本为 `S0`、盖章值为 `P`：

| 关系 | 动作 |
|---|---|
| `S0 < P` | 执行边界高于 `S0` 的各步迁移（可能为零步），版本键写为 `P` |
| `S0 = P` | 不写文件 |
| `S0 > P` | 不写文件、不迁移。发布版本上告警（降级，§4.5）；开发构建上不告警（读到发布版本盖过的文件是常态） |

由此，「程序更新后版本键变为新版本、其余内容不变」对发布版本成立；开发构建只在有迁移要做时才写文件。

## 3. 改写文件

### 3.1 流程

在 `loadFile` 内、`mergeYAML` 之前：

1. 读文件得 `data`，`yaml.Unmarshal` 得 `m`。读取失败、解析失败时行为同现状（`FileReadFailed` / `FileParseFailed`），不改写、不迁移、不重建。
2. 由 `m["config-version"]` 得文件版本 `S0`（§2.2），与盖章值 `P` 比较（§2.4），定出要执行的迁移步骤。
3. 值层：在 `m` 的副本上执行各步迁移、把版本键设为 `P`，得 `m'`。**本次运行一律把 `m'` 交给 `mergeYAML`**，与文件有没有写成无关。
4. 改写前的显式检查，任一不过即不写文件：
   - `data` 是合法 UTF-8（`utf8.Valid`）。带 BOM 的 UTF-16 能被 yaml 解析，按字节改写却会写坏。
   - 只有一个文档（`yaml.Decoder` 第二次 `Decode` 返回 `io.EOF`）。`yaml.Unmarshal` 只解析第一个文档且不报错，后面的文档它与第 6 步的校验都看不见，逐行改写却会动到它们。
   - 迁移步骤改过的每个键（本次即各 offset 键），在文本里恰好对应一行 §4.2 认得的整数键行。这一条只管迁移改过的键，不管版本键。
   - 版本键已存在时，在文本里恰好对应一行 §3.2 认得的版本键行；不存在时是插入新行，无须对应。
5. 文本层：把迁移改过的键写回各自的行，版本键按 §3.2 的专用规则替换或插入，得 `data'`（§3.2、§4.2）。
6. 校验：`yaml.Unmarshal(data')` 的结果须与 `m'` 完全相同（`reflect.DeepEqual`），不同即不写文件。
7. 把 `data'` 写进文件，步骤见 §3.6：有迁移步骤的走「迁移」一路，只改版本键的走「只改版本键」一路。

不写或写入没有完成时记一条告警，本次仍按 `m'` 运行，服务照常启动；磁盘上是什么、下次启动怎样，逐步列在 §3.6 的表里。正常情况下文件只有两种状态：整体换成 `data'`（已带新版本号），或仍是原样。不存在迁了一半或迁两遍。

### 3.2 文本层的保留规则

- 按字节处理，逐行切分并保留每行自己的行尾（CRLF、LF 混用也原样），不重新序列化：注释、键序、缩进、空行都不变。
- 版本键有专用的识别与替换规则，与 §4.2 的整数键行无关。认得的版本键行是「`config-version` + 冒号 + 同一行内的值 + 可选的行尾注释」，值可以带双引号、单引号或不带引号，带不带 `v` 都行，也可以为空或是别的类型（如手改成 `4.0`）。替换时把冒号之后、行尾注释之前的部分整体换成带引号的盖章值，行首缩进、冒号前后的空白与行尾注释保留。例：`config-version: "v4.0.0"`、`config-version: "4.0.0"`、`config-version: v4.0.0  # 勿改` 升到 4.0.1 后分别是 `config-version: "v4.0.1"`、`config-version: "v4.0.1"`、`config-version: "v4.0.1"  # 勿改`，其余字节不变。
- 版本键不存在：在第一个既非空行也非注释的行之前插入两行（一行注释、一行键）加一个空行，行尾取文件第一行的行尾，文件里没有行尾时取 LF。UTF-8 BOM 在第一行行首，不受影响。
- 认不了的写法由三道分别拦住，都落到「不写文件，每次启动在内存里换算并告警」：
  - 显式检查（§3.1 第 4 步前两条）：非 UTF-8 编码、多文档。这两种校验拦不住，只能显式查。
  - 「恰好对应一行」（第 4 步后两条）：流式写法、带引号的键、锚点与别名、合并键、键与值分行、超出 §4.2 所列的数值写法（找不到对应行）；嵌套映射或块标量里另有同名的行（对应到不止一行）。版本键同理：键带引号、值另起一行、写在流式映射里，都找不到认得的版本键行。
  - 校验（第 6 步）：其余改动了解析结果的情形，例如被当作「注释掉的键」改写的行其实是块标量的内容。

### 3.3 各种状态下的动作

| 状态 | 动作 |
|---|---|
| 没有 config.yml | 按模板生成（`FileGenerated`），模板里的版本键即 `P`；不迁移。同目录有备份时提示（§3.6 末） |
| 生成失败、读取失败、解析失败 | 同现状，不碰文件 |
| 正常加载，`S0 = P` | 不写 |
| `S0 < P`，没有适用的迁移步骤 | 只改版本键，不留备份（§3.6） |
| `S0 < P`，有迁移步骤 | 原文件改名为备份，迁移与改版本键一次写入（§3.6） |
| 非 UTF-8、多文档、文本层认不了的写法、校验不过 | 不写文件：告警，原文件不变，本次按 `m'` 运行 |
| 文件只读、目录不可写、文件被占用、加载期间文件被改写 | 写入失败或放弃：告警，原文件不变，本次按 `m'` 运行 |

### 3.4 模板与随包文件

- 模板 `defaultConfigContent` 加版本键一行，值为占位符；`DefaultConfigContent` 与 `generateDefaultConfig` 接收程序版本并代入盖章值，`Load` 相应接收程序版本（`main` 传 `Version`）。
- `tools/genconfig` 加一个版本参数，两个 workflow 的 `Prepare files for packaging` 步骤传入各自的 `VERSION`：发版得到 `"v4.0.0"` 这样的值，CI 开发构建的非 semver 版本号得到边界值；不传时同开发构建。
- 仓库根的 `config.yml` 是模板的副本，随模板同改。

### 3.5 与 `ConfigFileState`、横幅的关系

`FileState` 的五个取值不变，它回答的是「读到了没有」。改写的结果另记在 `Config` 的新字段里：改写前的文件版本 `S0`（§5 的判定要用）、本次启动留下的备份的路径、改写结果（未改 / 只改版本键 / 已迁移 / 应改而未写成 / 文件版本高于程序）。横幅据此在配置文件行之下另起一行、缩进加注，例如「v3 → v4.0.0，已迁移，原文件备份为 …」「v3 → v4.0.0：应迁移而未能写入，本次在内存中换算」「目录里另有备份 …，原有设置可能在其中」；路径行上只留加载结果的短注（如「（本次新生成）」），带备份文件名的附注接在路径后面会超出终端宽度而折行。`bannerConfigFileLine` 仍只读 `cfg`，不另算。

### 3.6 写入：改名即备份，不存在才放置

不用「先复制出备份、再覆盖原文件」：比对与覆盖之间总有一段时间，其间被保存的内容会被覆盖且没有副本。改为两个原语，三条写入路径都只用它们：

- **改名即备份**：先用 `os.CreateTemp` 在同目录按 §4.4 的模式预留一个备份名（得到一个只属于本次操作的空文件，名字每次不同），再 `os.Rename` 把 config.yml 改到这个名字上。同目录内改名是原子的，移走的就是那一刻实际在位的那一份，不需要比对。`os.Rename` 在两个平台上都会覆盖已存在的目标（`config/fileprimitives_test.go` 实测），这里被覆盖的只能是自己刚预留的空文件。改名失败（例如 config.yml 已不在）时删掉这个空的预留文件。
- **不存在才放置**：新内容先完整写进 `os.CreateTemp` 在同目录建出的临时文件（模式 `config.yml.*.tmp`；写入、`Sync`、关闭），再用 `os.Link` 把它链接为 config.yml，然后删掉临时名。`os.Link` 在目标已存在时失败且不动它（实测），成功时出现的就是完整的文件，没有写到一半的状态。

**每次操作只碰自己持有的名字**：临时文件与备份名都由 `os.CreateTemp` 独占地建出（实测：同一模式连续调用得到互不相同、已存在的空文件），本程序的另一个实例拿不到同一个名字。一次操作只链接（或改名）自己写的那个临时文件，只清理自己建的临时文件与预留名，不清理 config.yml 这个公共的名字，也不按名字模式去清理任何别的文件。两个实例同时启动时的各种交错见本节末。

`os.Link` 因文件系统不支持硬链接（FAT32、exFAT 等）而失败时，退回**不覆盖的改名**：把临时文件直接改名为 config.yml，目标已存在即失败且两者都不动，成功时临时文件整份到位，同样没有写到一半的状态。Windows 上是不带任何标志的 `MoveFileEx`：不带 `MOVEFILE_REPLACE_EXISTING`，所以不覆盖（`os.Rename` 带着它）；不带 `MOVEFILE_COPY_ALLOWED`，所以不会退化成复制加删除（`config/replacefile_windows_test.go` 实测，NTFS）。经改名放置之后临时名已随改名移走，这个名字不再属于本次操作，其后不再按它删除：别的实例的 `os.CreateTemp` 可能恰好生成了同一个名字，被删的会是它的文件。放回备份时同理，经改名放回的不再删备份名。标准库里没有不覆盖的改名，这一个操作按平台分文件实现；非 Windows 平台不设退路，硬链接失败即放置失败。`config` 包仍可在 `GOOS=linux` 下构建（Linux 只需可构建，常见的文件系统都支持硬链接），未在 Linux 上实跑。

不用 `os.OpenFile` 带 `O_CREATE|O_EXCL` 直接创建并写入，虽然它同样不覆盖、任何文件系统都可用：写入不是原子的。进程在写入中途崩溃会留下不完整的 config.yml，它可能仍能解析、只是少了后面的键，而文件头的版本键已是新值，下次启动发现不了；写入中途出错则要删掉没写完的文件，而关闭句柄与删除之间别的程序若把 config.yml 换成新内容，被删掉的是那一份，它没有任何副本。所以 **config.yml 这个名字上不做创建、写入或删除**：它只经改名离开原位，只经硬链接或不覆盖的改名出现。

放置时发现 config.yml 已存在（改名之后别的程序新建了它）：不覆盖，删掉临时文件，按「文件在变」处理，本次不再尝试。此时两份都在：备份名下是被本程序移走的那一份，config.yml 是别的程序刚建的那一份。

没有 config.yml 时按模板生成（`generateDefaultConfig`）同样改用不存在才放置，不再直接写入；放置时发现 config.yml 已出现，就改为加载那一份。临时文件总在改名之前写好，使「没有 config.yml」的时间只剩相邻的几步。

崩溃留下的临时文件（`config.yml.*.tmp`）与空的预留备份名不自动清理。按名字清理会删掉别的实例正在用的那一个；只清理「足够旧」的要另定时限并依赖时钟。它们只在写入的几步之间崩溃时才会留下，体积很小，名字可辨认，README 里说明程序未运行时可手动删除。

**迁移**（§4；`data` 是加载时读到的字节）：

| 步骤 | 这一步失败 | 这一步之后崩溃，磁盘上有 | 下次启动 |
|---|---|---|---|
| 1. 写临时文件（内容 `data'`） | 文件没动；本次内存换算 | 原 config.yml，可能有临时文件 | 重走迁移 |
| 2. 预留备份名，config.yml 改名过去 | 文件没动，删掉空的预留文件；本次内存换算 | 没有 config.yml；备份是原文件 | 按模板生成，并提示有备份（见下文） |
| 3. 读备份，与 `data` 比对 | 不同（加载之后被保存过）或读不出：把备份放回 config.yml，本次内存换算 | 同上 | 同上；已放回的重走迁移 |
| 4. 临时文件放置为 config.yml | config.yml 已存在：两份都在，本次内存换算 | config.yml 是迁移结果，备份是原文件 | 正常加载，不再迁移 |
| 5. 删临时文件 | 留下一个无害的临时文件 | 同上 | 同上 |

第 3 步的「放回」同样是不存在才放置（源是备份文件，成功后删掉备份名）；放回时 config.yml 又出现了，就两份都留。第 4 步遇到 config.yml 已存在时，那一份多半是用户刚保存的旧写法文件，下次启动对它重走迁移，先前移走的那份作为多出来的备份留着。

**只改版本键**（没有迁移步骤，不需要留备份）：步骤同上表，备份名也照 §4.4 预留，只在最后多一步「删掉备份」，删的是本次操作自己预留并改名得到的那一个。只有第 4 步自己的放置成功之后才删；第 3 步已确认它与 `data` 逐字节相同，而刚放上去的新文件与 `data` 只差版本键一行，删掉不丢任何内容。第 4 步因 config.yml 已存在而没有放成时，备份留着不删。任何一步之后崩溃，留下的是一份名字如实的备份，处理同上表。

**强制重建**（§5.4）：

| 步骤 | 这一步失败 | 这一步之后崩溃，磁盘上有 | 下次启动 |
|---|---|---|---|
| 1. 写临时文件（内容为模板） | 文件没动；不重建 | 原 config.yml，版本已是 `V` | 不再重建（§5.7） |
| 2. 预留备份名，config.yml 改名过去 | 文件没动，删掉空的预留文件；不重建 | 没有 config.yml；备份是被替换的那一份 | 按模板生成，正是重建要的结果 |
| 3. 临时文件放置为 config.yml | config.yml 已存在：两份都在，不重启 | config.yml 是模板，备份是被替换的那一份 | 正常加载，不再重建 |
| 4. 删临时文件 | 留下一个无害的临时文件 | 同上 | 同上 |

重建不做比对：被替换的是哪一份，备份里就是哪一份。

**没有 config.yml 而目录里有备份**：上表里「没有 config.yml」的几格，下次启动都按模板生成。这对重建是期望的结果；对迁移与只改版本键，用户的设置在备份里。程序不自动把备份放回去：它分不清这是上次写入被打断，还是用户有意删掉 config.yml 以重新生成（§5.7 给出的人工补救正是这样做）。改为告知：按模板生成时，同目录若有 `config.backup-*.yml`，告警并在横幅的配置文件行之下另起一行加注，写出最新一份非空备份的名字，说明原有设置可能在其中。

**两个实例同时启动**：配置处理早于端口绑定，端口冲突挡不住第二个实例走到这里。记用户的原文件为 U，两个实例为 A、B，各自的临时文件为 tA、tB，各自预留的备份名为 bA、bB。三条性质使任何交错下 U 都至少留有一份完整副本：

- 改名的目标是各自独占预留的名字，盖不到别的实例的备份；
- config.yml 只经不存在才放置出现，盖不掉在位的文件；
- 一次操作只删自己的临时文件、自己预留的空文件，以及（只改版本键且自己放置成功之后）自己那份与 `data` 逐字节相同的备份。

时间线一：A 只改版本键，B 见没有 config.yml 而按模板生成。初始 U 含 `config-version: "v4.0.0"`、`addr: "127.0.0.1:9000"`、`offset: -123`。

| 步骤 | 之后磁盘上 |
|---|---|
| A 以 4.0.1 加载 U，写好 tA（U 改版本键），预留 bA，改名并核对通过 | bA = U；tA；没有 config.yml |
| B 启动，见没有 config.yml，写好 tB（模板）；它不碰 tA | bA = U；tA；tB |
| A 放置 tA，随后删 tA、删 bA | config.yml = 改过版本键的 U；tB |
| B 放置 tB：config.yml 已存在，不覆盖；删 tB，改为加载 config.yml | config.yml = 改过版本键的 U |

若 B 先于 A 放置：config.yml 是模板，A 的放置因已存在而失败，bA 不删。U 完整留在 bA，A 告警并给出它的路径。

时间线二：A、B 同时重建。初始 U 没有版本键，含 `offset: 0x1f4`、`addr: "127.0.0.1:9000"`；两者都以 4.0.0 启动，`Load` 都没有落盘，网关返回 `v4.0.0`。

| 步骤 | 之后磁盘上 |
|---|---|
| A、B 各写好模板 tA、tB，各预留 bA、bB（名字不同，都是空文件） | config.yml = U；bA、bB 为空 |
| A 改名 | bA = U；没有 config.yml |
| A 放置 tA | config.yml = 模板；bA = U |
| B 改名：移走的是 A 放上的模板，落在 bB，碰不到 bA | bA = U；bB = 模板；没有 config.yml |
| B 放置 tB | config.yml = 模板；bA = U；bB = 模板 |

若 B 的改名落在 A 的改名与放置之间：config.yml 不在，B 的改名失败，B 删掉空的 bB 与 tB，本次不重建。两种顺序下 U 都在 bA。

时间线三：A、B 同时迁移。初始 U 没有版本键，含 `offset: 200`，两者加载到的都是 U，迁移结果记作 M。

| 步骤 | 之后磁盘上 |
|---|---|
| A 改名，核对通过，放置 M | config.yml = M；bA = U |
| B 改名：移走的是 M | bA = U；bB = M；没有 config.yml |
| B 读 bB，与自己加载时的 U 不同，把 bB 放回 | config.yml = M；bA = U |

B 本次按内存里的换算运行。若 B 的改名落在 A 的改名与放置之间，B 的改名失败，删掉空的 bB，同样按内存换算运行。U 都在 bA。

时间线四：A 迁移，B 同时重建（B 加载之后用户又把 v3 的旧文件存了回去，A 加载到的是它，仍记作 U）。B 先改名：bB = U，A 的改名失败、按内存换算运行，B 放上模板。A 先改名并放上 M，B 再改名：bA = U、bB = M，B 放上模板，与单个实例「迁移之后紧接着重建」的结果相同。B 的改名落在 A 的改名与放置之间：B 的改名失败，本次不重建（§5.7），A 照常放上 M。各种顺序下 U 都在某一份备份里。

**不加跨进程的锁**。上述性质已保证不丢内容，竞争的后果只是某个实例本次没有把迁移落盘或本次没有重建（下次启动重试，或按 §5.7 处理），或多留一份备份。锁文件要处理崩溃后残留的锁，处理不好会挡住启动；文件锁的系统调用因平台而异，在须能以 `GOOS=linux` 构建的 `config` 包里得按平台各写一套。两个实例同时启动本身该不该被阻止，不在本项范围。

## 4. 自动迁移

### 4.1 步骤表

迁移步骤是代码里一张按边界升序排列的表，每项含边界版本、值层函数与该步自带的注释替换（§4.3）；文本层对各步通用，只把值层改过的键写回对应的行。`S0` 低于某项的边界即执行该项，按序执行。本次只有一项：边界 `4.0.0-0`，把 `offset` 与各已注册播放器的 `<player>-offset` 取反。以后新增语义变更就在表尾加一项，不改已有项。迁移与改版本键在同一次写入里完成（§3.1），所以不会迁两遍。

### 4.2 各种写法

值层只动解析为 `int` 的值（与 `mergeYAML` 采纳的范围相同）。文本层不自行判断哪些键该改：它只把值层改过的键写回对应的行，认得的键行是「键 + 冒号 + 可带正负号的十进制整数 + 可选的行尾注释」这一种。以下解析结果均由 `config/yamlforms_test.go` 实测：

| 写法 | 值层 | 文本层 |
|---|---|---|
| `offset: 200` / `offset: +200` | 变为 -200 | 写成 `offset: -200` |
| `offset: -300` | 变为 300 | 写成 `offset: 300` |
| `offset: 0` / `offset: -0` | 不变 | 不改 |
| `offset: 200 # 说明`、整体缩进 | 同上 | 只换数字，缩进、间距、行尾注释保留 |
| `"200"`、`'200'`、`200.0`、空值 | 类型不符，本就被拒：不动 | 值层没改，不碰该行 |
| `9223372036854775808`（超过 int64 上限，解析为 `uint64`） | 不是 `int`，本就被拒：不动 | 值层没改，不碰该行；不妨碍其它键 |
| `-9223372036854775808`（`int` 的最小值） | 取反会溢出回它自己：改为饱和取反，得最大值 9223372036854775807 | 写成 `offset: 9223372036854775807` |
| `0x10`、`1_000`（yaml 解析为整数） | 取反 | 找不到认得的键行：不写文件，本次在内存里换算并告警 |
| 被注释掉的键，如 `# qqmusic-offset: 350` | 不在解析结果里 | 整行恰为「`#` + 上述键行」且数字是规范的十进制写法时同样取反，否则不动；带前导零的（如 `# kugou-offset: 01000`，yaml 按八进制解析为 512）不动 |
| 重复的键 | 整份文件解析失败，到不了迁移 | 同左 |

最小值用饱和取反而不按类型不符拒收，理由：旧语义下它是「延后到极限」，新语义下的最大值含义相同（只差 1 毫秒）；值层与文本层得到同一个数，校验照常通过；每次启动的结果一致。若改成拒收，文件里的那一行不动，盖上新版本号之后的下一次启动它又会被当作合法整数采纳，且方向相反。普通取反对它是错的：值不变而版本已盖，等于把「延后到极限」静默变成「提前到极限」。

注释掉的键也取反（数值超出 `int` 范围的不动），是因为用户日后取消注释时，它会按新语义生效；这一条无法经校验确认，也没有解析出的原值可对照，所以只认整行匹配，且数字去掉前导的 `+` 之后须与它的十进制写法逐字相同。`# kugou-offset: 01000` 取消注释后是八进制的 512，照十进制取反会写成 -1000，所以这类行不动；`-0` 同样不动，它的值本来就不变。命令行传入的 `-offset`、`-<player>-offset` 不经文件，从 4.0 起按新语义，不迁移。

### 4.3 旧注释

对 `config/config.go`、`main.go`、`config.yml` 的全部历史检索，模板里说明方向的句子只有两种：`正值=歌词提前，负值=延后` 与 `正值=歌词提前`。迁移时把注释行里的这两个短语整体换成 `正值=延后，负值=提前` 与 `正值=延后`，其余注释不动。此外，迁移写入的版本键注释多带一行，说明自 4.0 起 offset 表示延迟、本文件的 offset 已在迁移时取反；用户改写过那句旧注释时，至少文件头有这一行。

### 4.4 备份

- 备份不是另外复制出来的：迁移与强制重建都把原文件直接改名成备份（§3.6），备份就是被替换的那一份。只改版本键的写入途中用同样的名字，成功后删掉，不留备份。
- 位置与名字：与 config.yml 同目录，`config.backup-<版本>-<本地时间 yyyyMMdd-HHmmss>-<随机段>.yml`，随机段由 `os.CreateTemp` 填入（模式里的 `*`）。`<版本>` 是本进程所知的该文件的版本，取规范形式（带 `v`，如 `v4.0.0`），没有版本键的写作 `v3`，版本键非法的写作 `unknown`；例如 `config.backup-v3-20261009-153045-1234567890.yml`。迁移时它是 `S0`；重建时是文件当时的版本（`Load` 写成了即盖章值，否则仍是 `S0`）。名字因此说明这份备份里的 offset 是哪种语义：低于 `v4.0.0-0` 的是旧写法，其余是新写法。保留 `.yml` 后缀便于直接打开；`configPath` 只认 `config.yml` 这一个名字，不会误读备份。
- 不会重名：名字不是先查后用，而是由 `os.CreateTemp` 独占地建出一个空文件来预留，再把 config.yml 改名到它上面（§3.6）。同一秒、同一版本的两次操作，乃至同时启动的两个实例，各自拿到不同的名字。预留成功而随后改名失败时，删掉这个空的预留文件；预留本身失败则放弃本次写入、下次启动重试。
- 不自动清理：迁移与重建只在跨过边界或门槛时发生，数量有限。迁移之后紧接着重建会留下两份，原文件（如 `…-v3-…`）与迁移后的文件（如 `…-v4.0.0-…`），都留着：名字里的版本已说明各自的语义，清掉哪一份都要多一步删除及其失败处理。

### 4.5 文件版本高于程序（降级）

不写文件、不迁移，告警并在横幅上加注；文件按当前程序的语义读取。不把版本键改低，否则用户再升回去会重迁。两个版本之间若隔着迁移步骤，取值的含义会不符，程序无法逆推它不认识的步骤。

4.x 之内的降级可能发生（`-force` 同步），照上述规则处理。已定的判断（2026-10-09）：此后不预期再有破坏性的配置变更，从 v2 至今只有这一次方向改动，所以 4.x 之间不会隔着迁移步骤，降级后的取值含义不变。

旧程序读到 `config-version` 不会出错：`v3.3.4` 与当前的 `config/config.go` 都是解码进 map 后只读认得的键，没有严格模式，也不遍历全部键，不认识的键直接忽略。

降回 3.x 时上述规则不起作用：3.x 没有这段逻辑，会按旧语义读已取反的 offset，歌词偏差为两倍 offset。旧程序改不了，只能在流程上避免。已定（2026-10-09）：4.0 发布后不再降回 3.x，写进发版说明与 AGENTS.md §12。

### 4.6 v2 时期的配置：能做到的与做不到的

- 能做到：文件里写了的 offset 取反，这位用户看到的歌词时刻与升级前相同；盖上版本号。
- 做不到：缺的键仍落到 `DefaultConfig()`。没写 `<player>-offset` 的播放器继续用全局值（新默认 -200），拿不到模板的 -500 / -400 / -430 / -340 / -400；模板后来新增的键与说明也不会出现在文件里。

迁移不往用户的文件里加配置键：无法区分「旧模板里没有」与「用户有意删掉」，加键等于改了用户没写过的设置。这部分由 §5 的强制重建解决。

## 5. 强制删除重建（#32）

已定（2026-10-09）：触发后不询问用户，直接把旧文件留作备份、按模板写入新的默认配置。

### 5.1 网关字段

版本检查响应的顶层键 `config_force_update`，字符串，带 `v` 前缀的版本号（线上现值为示例 `"v3.7.0"`），客户端按与 `tag_name` 相同的方式规范化（`normalizeSemver`）。字段缺失、为空串或不是合法版本号，一律视为不强制。`releaseInfo` 加一个字段承接它；其现有标签 `tag_name`、`name`、`global_cdn_download_url_prefix`、`china_cdn_download_url_prefix`、`assets`（内含 `name`、`size`、`digest`）与线上响应的键名一致（2026-10-09 核对）。

### 5.2 升级时序

3.x 没有本设计的任何逻辑：它启动、检查更新、替换 exe、`restartSelf` 启动新版本并等它结束，全程不碰 config.yml。配置的处理全部发生在新版本的进程里，先后如下：

1. `config.Load`：读文件，把改写之前的版本 `S0` 记进 `Config`（§3.5）；随后自动迁移并把版本键改写为盖章值（§3、§4）。
2. 横幅、遥测初始化、隐私提示，照现行顺序。
3. `checkAndUpdate` 取得并解析响应，读出 `config_force_update`。
4. 判定（§5.3），位置在响应解析成功之后、是否更新的分支之前：凡拿到响应的进程都判一次。成立即重建（§5.4）。
5. 本次还要更新的，照常更新并重启；不更新而刚重建过的，提示后重启（§5.5）；其余继续启动。

**启动顺序不调整**，仍是先加载配置、后做版本检查，代价是 3.x 升上来且字段要求重建的那一次启动里，文件先被迁移、十几秒后又被模板取代，多写一次，并留下两份备份（§4.4）。不调整的理由：横幅与遥测初始化都要用已加载的配置，而遥测初始化与隐私提示须早于版本检查（AGENTS.md §1.2），版本检查挪不到加载之前；另一种做法是 `Load` 只在内存里换算、把写文件推迟到版本检查之后，那要让 `Config` 挂着一份待写内容，并在 `checkAndUpdate` 的每条返回路径上补写，漏接一处，文件就永远不落盘且不报错。

顺序不变带来的要求：**判定只用第 1 步记在内存里的 `S0`，不得重读文件**。那时磁盘上的版本键已是盖章值，重读会得出「已是新版本」而不重建。第 4 步放在更新分支之前也是为此：进程若先盖了版本号、接着去更新而不判定，下一个进程读到的 `S0` 就是它的盖章值，原先的版本信息丢失。放在分支之前则没有这个缺口：字段不高于本进程版本时本进程当场重建；字段高于本进程版本时，本进程的盖章值仍低于字段，之后升到不低于字段的版本时照常成立。

以下情形拿不到响应，只有自动迁移：非发布版本（`checkAndUpdate` 开头即返回）、连不上网关、响应非 200 或解析失败。其中新版本第一次启动恰好拿不到响应的，文件已盖上新版本号，之后不再重建。无网启动基本不会发生，这一情形按接受处理，不加机制（§5.7）。每日心跳不解析响应（`heartbeatinert_test.go`），不会触发重建。

### 5.3 判定规则

已定（2026-10-09）：按门槛判定。记字段为 `F`、程序版本为 `V`、改写之前的文件版本为 `S0`：

**`S0 < F` 且 `F <= V` 时强制重建，否则只做自动迁移与盖版本号。**

字段的含义因此是「低于此版本的配置须重建」，设一次即可，不必随每次发版改动。前提：`F` 合法（缺失、空串、解析不了即不强制）；`S0` 已知（文件本次正常加载；本次新生成的、读取或解析失败的不判）；`F` 高于本进程树已处理过的门槛（§5.5 的标记，没有标记即视为满足）。

`F` 高于 `V` 时不做：本程序的模板比 `F` 要求的旧。此时本进程的盖章值仍低于 `F`，等程序升到不低于 `F` 的版本，首次启动时照常成立。

线上现值代入（`V` = 3.3.4、`F` = 3.7.0）：`F > V`，不强制（3.3.4 也没有这段逻辑）。示例值若保留到 4.0 发布，没有版本键的配置（`S0` = 3.0.0 < 3.7.0 ≤ 4.0.0）同样会在 4.0 首次启动时重建。

已定（2026-10-09）：4.0 发布时字段取 `v4.0.0`。4.0 要先经过 alpha、beta、rc 才到正式版，这个取值在预发布阶段的后果如下：

- 预发布版本的程序（`4.0.0-alpha.N`、`4.0.0-beta.N`、`4.0.0-rc.N`）都低于 4.0.0，满足不了 `F <= V`。**预发布阶段不会强制重建，只做自动迁移与盖版本号。**
- 4.0.0 正式版首次启动时，v3 配置（`S0` = 3.0.0）与预发布版本盖过的配置（`S0` = `4.0.0-rc.N` 等，低于 4.0.0）都重建一次。
- 若要预发布阶段就走到重建，须把字段设为首个带本功能的预发布版本号（如 `v4.0.0-alpha.1`）。那样正式版时 v3 配置照样重建，已在预发布阶段重建过的（`S0` 不低于该预发布版本）不再重建。本设计不采用这种取值，只作说明。

设 4.0.0 发布时 `F` = 4.0.0，之后发 4.0.1 而 `F` 未动：

| 情形 | 结果 |
|---|---|
| 3.x 升 4.0.0，之后再升 4.0.1 | 4.0.0 首次启动时重建；升 4.0.1 时 `S0` = 4.0.0，不动 |
| 3.x 跳过 4.0.0 直接到 4.0.1 | `S0` = 3.0.0 < 4.0.0 ≤ 4.0.1，重建 |
| 4.0.0 时已重建、之后自己改过，升 4.0.1 | `S0` = 4.0.0，不动，改动保留 |
| 把 `F` 改成 4.0.1 | 配置低于 4.0.1 的，在首次以 4.0.1 启动时重建（自己改过的设置换成默认，有备份）；改字段之前已跑过 4.0.1 的，`S0` = 4.0.1，不动 |
| 同一版本反复启动 | 重建写出的文件版本即 `V`，此后 `S0` = `V`，不低于 `F`，不再重建 |
| 4.0.0 的进程读到 v3 配置，同时还有 4.0.1 可更新 | 先判定：`F` = 4.0.0 ≤ `V`，当场重建，再更新；4.0.1 的进程读到 `S0` = 4.0.0，不动 |
| 新版本第一次启动拿不到响应 | 文件已盖上 `V`，此后不重建（§5.7，已接受） |
| 判定成立而备份或写入失败 | 文件已盖上 `V`，此后不重建（§5.7，已接受）；告警里给出人工补救 |
| 版本已发布、用户跑过之后才设 `F` = `V` | `S0` = `V`，不成立。补救：发一个补丁版本，把 `F` 设为它 |

### 5.4 动作

`Load` 与重建之间隔着隐私提示的等待与网关请求，其间 config.yml 可能被用户保存过。重建因此不假定文件还是 `Load` 留下的样子，也不做任何比对，直接照 §3.6「强制重建」一路执行：

1. 按模板（代入盖章值）写好临时文件。
2. 预留备份名，把 config.yml 改名过去。此刻在位的是哪一份，备份里就是哪一份，`Load` 之后被保存过的内容也在其中。
3. 把临时文件放置为 config.yml；config.yml 又出现了就不覆盖。
4. 读备份，供提示使用（§5.6）；告知用户。本次还要更新的接着更新，由更新后的重启带出新进程；不更新的直接重启（§5.5）。

没有会被覆盖而不留副本的时刻：旧内容只经改名离开原位，新内容只在原位空着时放进去。

迁移之后紧接着重建会有两份备份：`Load` 改名留下的原文件，与这里改名留下的迁移后的文件，都留着（§4.4）。提示里以后一份为准，它已是新写法。

第 1、2 步失败时文件没动；第 3 步因 config.yml 已存在而失败时，备份与别的程序新建的那一份都在。三种情形都告警，不因重建而重启，以已加载的配置继续运行（要更新的照常更新），后续见 §5.7。

### 5.5 重启与防循环

进程里加载的仍是旧配置，横幅也已按旧配置打印，`Load` 注册全局 flag、不能再调一次，所以与自动更新一样走 `restartSelf`。此刻调用是安全的：`checkAndUpdate` 早于 `srv.Start`、心跳与音频管理器（AGENTS.md §1.2），端口未绑定，没有需要收尾的状态；与更新后重启的差别只是 exe 没有被替换，原进程等待期间占用的就是 exe 自身，不影响以后的更新。更新后紧接着重建时进程链多一层（旧版本进程等新版本进程，后者再等重建后的进程），等待中的进程不做任何事。

不会循环，论证分两层：

- 规则本身：重建写出的文件，版本键是本进程的盖章值 `V`，而判定成立时 `F <= V`。重启出来的进程读到 `S0` = `V`，不低于 `F`，同一个门槛不会第二次成立。
- 硬闸：重建后、重启前（含随后由更新带出的重启）设两个环境变量，`PLAYERCAP_CONFIG_REBUILT` 记本次处理的门槛 `F`，`PLAYERCAP_CONFIG_BACKUP` 记备份路径。带标记的进程拿到响应时，响应里的门槛不高于标记所记的值就跳过判定，更高则照常判定。同一棵进程树里，同一个门槛至多处理一次，与文件内容无关：模板漏了版本键、盖章值算错这类缺陷也只多重启一次。

标记只挡不高于已处理值的门槛，是因为更高的门槛是合法的新要求。例：4.0.0 的进程按 `F` = 4.0.0 重建后更新到 4.0.1，新进程拿到的响应里 `F` 已是 4.0.1；这时文件版本 4.0.0 低于门槛，应当再重建一次。一棵进程树里的重建次数受「门槛严格升高」限制，仍是有限的。

### 5.6 告知用户

重启前在控制台打印一个方框（样式同自动更新），任务栏闪烁，随后在方框之下逐秒倒计时 10 秒（用的是隐私提示的那一行倒计时，结束后该行被擦掉）。方框里写：配置已按当前版本的模板重建；旧配置备份的文件名（带随机段，须原样给出）并说明它与 config.yml 同目录；旧文件与新模板取值不同的键，逐行写作「键: 原值 → 重建后的值」；程序将重启以加载新的 config.yml。备份的完整路径不进方框（太长，折行后续行没有左边框），写在方框上方重建成功的那行日志里。

「原值」一律是新语义下的值，不直接取磁盘上的字面：把 §5.4 第 2 步改名留下的备份（即被替换的那一份）解析后，按它自己的版本键做一遍值层迁移（与 `Load` 用的是同一个函数），再与模板逐键比较。这样无论文件有没有被迁移落盘都对：`Load` 写成了的，它已是新写法，值层不再动它；文本层认不了而没写成的（如 `offset: 0x1f4`），它仍是旧写法，值层在这里换算。列出的原值因此可直接照填。备份解析不了时不列差异，照实说明。

备份文件里的 offset 是哪种语义，按备份内容自己的版本键照实写（不看名字，名字里的版本在文件被别的程序改过时可能不准）：低于边界的，提示「备份里的 offset 仍是旧写法（正值=提前），请以上面列出的值为准」；否则提示它已是新写法。

新进程读到 `PLAYERCAP_CONFIG_BACKUP` 时，在启动完成处再提示一行（已重建、备份的完整路径），使它留在屏幕的最后几行。

### 5.7 不会再重建的两种情形（已接受）

以下两种情形里，文件已盖上新版本号 `V` 而没有换成新模板，此后 `S0` = `V`，门槛不再成立。两者都按接受处理，不加机制：

1. 新版本第一次启动拿不到网关响应（§5.2）。
2. 判定成立而重建没有成功：写临时文件或改名失败，或放置时发现 config.yml 又被别的程序建了出来（§5.4）。

第 2 种考虑过留下可重试的状态：失败时把文件恢复为本进程改写之前的字节，使下次启动重走迁移与判定（只把版本号改回去不行，已取反的 offset 会再迁一遍）。不采用，理由：重建失败的原因是目录不可写、磁盘已满、文件被占用或被别的程序反复保存，恢复要动的是同一个文件，多半同样失败；恢复还意味着替换掉此刻在位的文件，那可能正是用户刚保存的内容；它新增的失败面比要补的这一种情形更大。

人工补救对两种情形相同：删除 config.yml 后重启，程序按当前模板生成。第 2 种在失败的告警里写明这一做法，并给出已改名留下的备份的路径（没有则说明没有备份）；README 里同样写上。此外，之后的版本把 `config_force_update` 设得更高，这些文件也会被覆盖到。

### 5.8 考虑过而不采用的方案

- **等值判定**（字段等于当前程序版本才强制，即 `F == V` 且 `S0 < V`）。漏掉的：从 3.x 跳过该版本直接升到更晚版本的用户不会重建，仍用旧时期的配置。要补上只能每次发版都把字段改成新版本，而那样所有用户每升一版都被换成默认配置，自己改的设置一再被换掉。它还必须附带 `S0 < V`，否则同一版本每次启动都重建并重启。
- **多记一个「模板版本」键**（记录文件由哪个版本的模板生成，盖章与迁移都不改它，判定时代替 `S0`）。它能覆盖「新版本第一次启动拿不到响应」与「版本发布后才想强制」两种情形；前者已按接受处理，后者可发补丁版本补救。代价是文件里多一个由程序维护的键，以及它缺失、被手改、与版本键矛盾时的一组处理。
- **把写文件推迟到版本检查之后，或调整启动顺序。** 理由见 §5.2。
- **重建前询问用户。** 已定不询问：强制即强制，旧文件留有备份，提示里列出需要重新填写的设置。

## 6. 测试拆分与用例

### 6.1 拆分

逻辑拆成不碰网络、不碰全局状态的函数，全部放在 `config` 包（纯 Go，Linux 可跑）：读文件版本、盖章值、选迁移步骤、值层迁移、文本层改写、改写校验、备份命名、重建判定（入参为 `S0`、`F`、`V` 与已处理的门槛）、旧文件与模板的逐键比较。替换文件的各步（§3.6）经可注入的文件操作（预留、改名、链接、不覆盖的改名、读取、删除）执行，步与步之间留有钩子，以便逐步注入失败、中止，以及另一个实例的动作。`loadFile` 的整套流程沿用 `config/loadfile_test.go` 的做法，以注入的 `osExecutable` / `osGetwd` 指向临时目录驱动。

经真实 `Load()` 的用例放根包，用 `bannerconfig_test.go` 的 `loadConfig`：v3 文本加载后回显的 offset 为取反值、文件已改写、备份存在；命令行 `-offset -200` 与 `-offset=-200`；横幅配置文件行的加注。#54 的两个算式在 `player/` 包测：`AdjustLyricPlayTime` 与新函数各一组，另加一条 AST 门禁，要求六家播放器包都调用新函数且不再自行对 offset 做加减（比照 `player/positionsample_lint_test.go`）。

### 6.2 用例（含反例）

- 文件版本：无键；`"4.0.0"`、`4.0.0`、`"v4.0.0"`、`"V4.0.0"`、带首尾空白；`"4.0.0-beta.3"`、`"4.0.0-0"`、`"3.3.4"`、`"0.0.0"`；两段写法 `"4.0"`（`x/mod/semver` 是否接受简写由用例钉住）；非法：`4.0`（小数）、`4`（整数）、`""`、`"abc"`、布尔、列表、映射，均须判为「不迁移、改写版本键」。写入的形式恒带 `v`：读到 `"4.0.0"` 的文件在下一次改写版本键时写成带 `v` 的值；读到与盖章值相等而不带 `v` 的不为此单独写文件。
- 盖章值：`Version` 为 `0.0.0`、空串、CI 开发构建的非 semver 串（均得 `v4.0.0-0`）、`4.0.0`、`v4.0.0`（均得 `v4.0.0`）、`4.0.0-beta.3`（得 `v4.0.0-beta.3`）；模板与 `tools/genconfig` 的输出同此。
- 幂等：同一文件连续加载两次，第二次不写文件；开发构建连续两次；开发构建之后换发布版本（只改版本键、不再迁移）；发布版本之后换开发构建（不写、不改低）；`4.0.0-beta.3` 盖过的文件由 `4.0.0` 读取（不再迁移）。
- 文本层：§4.2 表的每一行；CRLF、LF、两者混用、末行无换行；UTF-8 BOM；只有注释的文件、空文件；首行为 `---`；版本键已存在且带行尾注释、带缩进；未注册播放器的 `foo-offset`（不动）；`#offset: 5`、`#  kugou-offset: -430 # x`、`# offset: +200`（取反）；`# kugou-offset: 01000`、`# offset: -010`、`#offset: 007`（带前导零，不动）；`# 例如 offset: 200 即可`（不动）；嵌套映射里的 `offset`、流式写法、带引号的键、锚点与别名、UTF-16（均须不写文件且原文件字节不变）；块标量里形如注释掉的键的行（由校验拦下）。多文档：`offset: 200`、`---`、`config-version: "v4.0.0"`、`offset: -500` 四行的文件须不写文件，第二个文档的字节不变，本次运行的 offset 为 -200。整数两端：`offset: -9223372036854775808` 迁移后值层与文件都是 9223372036854775807，再加载一次不变；`offset: 9223372036854775808` 不动且不妨碍同文件里其它 offset 的迁移。
- 只改版本键（§3.2 的专用规则）：没有适用的迁移步骤、文件里已有版本键，写法分别为 `"v4.0.0"`、`"4.0.0"`、`'v4.0.0'`、不带引号的 `v4.0.0`、带行尾注释、带缩进，升到 4.0.1 后只有该行的值变成 `"v4.0.1"`，其余字节逐一相同，目录里不留备份；版本键非法（`4.0`、空值）时同样只换该行；键带引号、值另起一行时不写文件。文件里同时有形状不合 §4.2 的 offset（如 `offset: 0x10`）而本次没有迁移步骤时，照常更新版本键（整数键行的检查只管迁移改过的键）。
- 写入的各步（§3.6 三张表逐格）：迁移、只改版本键、强制重建三条路径，每一步分别注入「失败」与「到此为止」（模拟崩溃），断言磁盘上的文件与表中所列一致，再以同一目录重新加载一次，断言结果与「下次启动」一列一致。其中须有：
  - 改名之后别的程序又新建了 config.yml：放置不覆盖，新建的那一份字节不变，备份是被移走的那一份，临时文件已删；迁移与只改版本键路径本次按内存换算运行，重建路径不重启。
  - 改名得到的那一份与加载时读到的不同（加载之后被保存过）：迁移与只改版本键路径把它放回 config.yml，内容是被保存过的那一份，不留备份，本次按内存换算运行，下次启动重走；放回时 config.yml 又出现了，两份都留。
  - 写临时文件失败、改名失败（文件只读、目录不可写）：原文件字节不变。
  - 硬链接不可用（注入 `os.Link` 失败且不是「已存在」）：退回不覆盖的改名，结果与硬链接一路相同；此时 config.yml 已存在同样不覆盖，那一份的字节不变。经改名放置（或放回）之后不再按空出的源名删除：在该名字处放一个哨兵文件，结束时它须仍在。硬链接与改名都失败：迁移与只改版本键两路把备份放回，放不回时原文件留在备份名下，重建不放回；其间别的程序建出的 config.yml 不被删除。
  - 替换 config.yml 的任何路径、任何注入的失败下，都不以 config.yml 的路径发起删除（夹具记下每一次删除的路径，用例结束时断言）。四条路径上逐个让第 n 次文件操作失败，用户的原文件都留有一份完整的副本。
  - 不覆盖的改名本身，在真实的文件系统上（Windows）：目标已存在时返回「已存在」，源与目标的字节都不变；目标不存在时源整份移过去，源名不再存在；源不存在时报错，目标不出现。
  - 各步之后崩溃留下「没有 config.yml、有备份」：下次启动按模板生成，告警与横幅加注写出最新一份非空备份的名字；目录里没有备份时不加注。
  - 目录里已有别的 `config.yml.*.tmp` 与空的 `config.backup-*.yml`（模拟崩溃遗留或别的实例在用）：本次操作不删、不读、不链接它们，结果不受影响；按模板生成时的备份提示跳过空的那些。
- 两个实例交错（§3.6 末的四条时间线）：不靠真实并发与睡眠，用步骤钩子在一个实例的指定两步之间执行另一个实例的若干步。每条时间线及其写明的另一种顺序各一例，逐步断言磁盘上的文件与表中一致，并断言结束时用户的原文件 U 有一份字节完整的副本（在 config.yml 或某一份备份里）。其中：
  - 时间线一：A 只改版本键、停在放置之前，B 走完按模板生成；A 先放置时最终 config.yml 是改过版本键的 U、没有备份、没有临时文件；B 先放置时 config.yml 是模板、bA 仍在且等于 U。
  - 时间线二：两个实例对同一个 v3 文件在同一秒重建，bA 与 bB 名字不同，U 在先改名的那一份里且没有被第二次改名盖掉。
  - 时间线三、四：后改名的实例移走的是前一个实例放上的文件，核对不同后放回，或改名因 config.yml 不在而失败并删掉自己的空预留文件。
- 重建不看文件是否变过：无版本键的文件含 `offset: 200` 与 `addr: "127.0.0.1:8765"`，加载（迁移，原文件改名为备份）之后把 `addr` 改成 `"127.0.0.1:9000"` 再重建，重建留下的备份里须有 9000；此时目录里有两份备份，名字里的版本分别是 `v3` 与盖章值。`Load` 只改了版本键、`Load` 没写成文件时重建，各留一份备份。
- 备份命名：`v3`、`v4.0.0`、带预发布后缀的版本、版本键非法时的 `unknown`；名字符合 `config.backup-<版本>-<时间戳>-*.yml`；同一秒、同一版本连续两次得到不同的名字，先前那一份的字节不变；预留成功而改名失败后，目录里不留空的预留文件。
- 重建提示（§5.6）：文本层认不了的 `offset: 0x1f4`（文件未落盘）之后强制重建，提示列出的原值须是 -500 而不是 500，并说明重建留下的备份是旧写法；迁移已落盘的文件，重建留下的备份是迁移后的那一份，列出的原值与它的字面相同，并说明它是新写法；备份的语义按内容的版本键判断而不看名字（备份名写着 `v3` 而内容已带新版本键时须说明是新写法）；备份解析不了时不列差异。
- 重建判定：§5.3 表的每一行；线上现值（3.3.4、3.7.0）；`S0` 等于 `F`（不成立）、`F` 等于 `V`（成立）、`F` 高于 `V`（不成立）三个边界；`F` 缺失、空串、`"abc"`、不带 `v`、带预发布；`S0` 未知；`V` 为开发构建。预发布阶段（§5.3）：`F` = `v4.0.0` 时，`V` 为 `4.0.0-alpha.1`、`4.0.0-beta.3`、`4.0.0-rc.2` 均不成立；`V` = 4.0.0 时，`S0` 为 3.0.0 与 `4.0.0-rc.2` 均成立，`S0` = 4.0.0 不成立；`F` = `v4.0.0-alpha.1` 时，`V` = `4.0.0-alpha.1`、`S0` = 3.0.0 成立，之后 `V` = 4.0.0、`S0` = `4.0.0-alpha.1` 不成立。已重建标记：标记所记门槛等于或高于响应里的门槛时跳过判定，低于时照常判定；连续两次不同门槛的响应（先 4.0.0 后 4.0.1，文件版本 4.0.0）第二次须成立；同一门槛的响应来两次，第二次须跳过，即使文件版本被人为改低。另有两条针对「版本号先被盖掉」：v3 文件经 `loadFile` 之后，磁盘上的版本键已是盖章值，而 `Config` 记下的改写前版本仍是 3.0.0，以它判定须成立；同一文件先后由 4.0.0、4.0.1 加载，第二次的 `S0` 为 4.0.0（钉住「盖了版本号而不判定，信息即丢失」这一前提）。
- 回显与事件：默认配置下 `play_time` 与改动前逐位相同（取 offset 为 ±200、0、大于时间戳的值各一例）。

### 6.3 计划注入的变异

边界由 `4.0.0-0` 改成 `4.0.0`；开发构建的盖章值改成 `0.0.0`；步骤选择的 `<` 改成 `<=`；去掉改写校验；迁移与改版本键分两次写；放置新文件时允许覆盖已存在的 config.yml；临时文件改回固定的名字；备份名改回先查后改名；写入前按名字模式清理别的临时文件；只改版本键路径在自己的放置没成功时也删备份；预留备份名成功而改名失败后不删空的预留文件；备份改回先复制再覆盖；迁移路径不核对改名得到的那一份，或核对不同也照写、不放回；只改版本键路径成功后不删备份，或未经核对就删；版本键已存在时按整数键行的规则去找它；整数键行的检查扩大到全部 offset 键而不限于迁移改过的；硬链接失败时不走不覆盖改名的退路；不覆盖的改名换成会覆盖的 `os.Rename`；放置失败后按 config.yml 的路径删除；经改名放置之后仍按空出的源名删除；被注释掉的键不要求规范的十进制写法；按模板生成时不提示目录里的备份；对字符串或小数取反；`int` 最小值按普通取反处理，或按类型不符拒收；文本层自行按键名改行而不看值层改了什么；去掉文档数量的检查；去掉 UTF-8 检查；降级时把版本键改低；非法版本键按 v3 处理；判定去掉 `F <= V` 或把 `S0 < F` 改成 `<=`；改写之后才记文件版本，或判定时重读文件；忽略已重建标记，或带标记即一律不判；重建提示的原值直接取磁盘字面，或备份的语义按名字判断；写入的版本键不带 `v`；模板里漏掉版本键；`AdjustLyricPlayTime` 或新函数的符号改回。每条都须有用例变红，结果记在用例注释里。

### 6.4 只能靠人守

`checkAndUpdate` 里判定与重建的调用点（须在更新分支之前，传入的须是 `Config` 里记下的改写前版本）、`restartSelf` 的调用（现有的更新路径同样没有门禁，AGENTS.md §3.5）；`releaseInfo` 新字段的 JSON 标签；两个 workflow 把 `VERSION` 传给 `tools/genconfig`；五家没有离线会话夹具的播放器传给新函数的位置是否正确（门禁只查有没有调用）；`MoveFileEx` 的标志须为 0（带上 `MOVEFILE_COPY_ALLOWED` 没有用例变红：同一卷内的改名用不到复制）。真机才能验的：重建提示在控制台上是否看得见、Windows 上只读文件与被占用文件的实际报错、记事本存出的各种编码、不支持硬链接的文件系统（FAT32、exFAT）上放置 config.yml 的实际表现（不覆盖的改名只在 NTFS 上实测过）。

## 9. 待定

以下各点需要定夺，每条列出各选项对用户的后果与建议。已定的事项不在此列：强制重建按门槛判定、4.0 发布时 `config_force_update` 取 `v4.0.0`（§5.3），4.0 之后不降回 3.x（§4.5），不加 `capabilities` 项（§8），版本键带 `v`（§2.2）。

1. **是否要一个不依赖网关的本地触发条件。** 本地能判断的只有「文件缺少模板里的键」。
   - 以它触发重建：有意删掉某些键的用户会被换成默认配置，而且没有网关字段那样的总开关可以关掉。
   - 只告警（列出缺的键，说明删掉 config.yml 后重启即可重建）：有意删键的用户每次启动都会看到这条告警。
   - 建议：不做本地触发的重建；告警也先不做。到不了网关的只有离线用户与开发构建，数量少，且仍有自动迁移。

2. **被注释掉的 offset 键是否一并取反（§4.2）。**
   - 取反：用户以后取消注释，歌词时刻与升级前写下它时相同。
   - 不动：文件里除生效的键外一字不改，但取消注释后方向相反，且没有提示。
   - 建议：取反。

3. **重建提示停留 10 秒（§5.6）。** 它使服务晚 10 秒启动，只发生在重建的那一次。停留更短，提示更容易被随后的横幅顶出视野。建议 10 秒。

4. **键名 `config-version`（§2.1）。** 改名只影响文件里那一行的写法，对行为没有影响；建议照此定名。
