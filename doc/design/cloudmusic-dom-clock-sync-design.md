# 网易云位置时钟按 DOM 跳秒对表设计

本文是 issue #77 的设计。cloudmusicv3 的位置时钟在换歌、暂停恢复、跳转之后与网易云界面上的进度不同步，各首歌早晚不一。改为在界面进度（DOM 上的整秒值）跳秒的时刻对表，并保留现有约 0.3s 的常态落后量；默认偏移与配置模板不动。

状态：已实施（`bb87244` 时钟、判定、未告知量及用例；`16e0c88` `runSession` 接线、回放用例与 AST 门禁；`43d0ee9` 代码审查后的两处修订：对外位置改取发出那一刻的读数，非换歌拍补发的歌词事件推迟到对表之后，§2.1、§3.4、§5.2、§5.3、§6 已按它改写）；真机回归已做（2026-10-09，结果见 §10.2 末与 issue #77 的评论）。实现与本文有两处出入：换歌那一拍与 DOM 读数成对的读写所配的时刻在分支之后重取（§2.1 写的是配 `got`；按 §1.2 与 §4.2，时钟须在分支之后才由 0 起走，这一拍本就不参与对表）；时钟多一个 `setPlaying` 方法承担起走与冻结（§6 只列了四个），「冻结取时钟读数、下限保留」因此有用例可守。

数据来源：2026-10-09 两次真机实测（issue #77 的两条评论），共 18 次换歌、2 次启动附着、3 次暂停恢复。探针在 DOM 秒数变化的那一拍打印「DOM 秒数 − 时钟」，下文称**读数**，正值为时钟落后。标「实测」的出自这两次；标「推断」的由代码或数据推得，未在真机见过。

## 1. 现状

### 1.1 时钟与轮询

均在 `player/cloudmusic/cloudmusic.go` 的 `runSession`。

- 位置 = `baseRealClock.GetCurrent()`：在走时为 `BaseRealTime + time.Since(AnchorTime)`，否则为 `BaseRealTime`；不钳时长。
- 轮询用 `time.NewTicker(EffectivePollInterval(p.pollMs))`。默认 `poll: 30` 被抬到 100ms（低于 50ms 一律 100ms），配置上限 2000ms（`config` 的 `pollMax`）。
- 每拍一次 `cdp.Client.Extract`：一次 `Runtime.evaluate`，读 Redux 的 `playingState`（2 为在播）与 `curPlaying`，以及 DOM 上 `.curtime-thumb` 的文本，按「分:秒」解析成整秒 `DomTimeSec`，解析不出为 −1。仓库内没有记载过比整秒更细的进度来源（§9.4）。
- 时钟只在四处被写：换歌分支置零；状态由非在播转为在播时起走；由在播转为非在播时冻结；seek 检测置为 `DomTimeSec`。

一拍之内的顺序：换歌分支 → Redux 歌词补取与超时兜底 → 更新时钟（起走 / 冻结）→ 歌词行匹配（`clock.GetCurrent() + offsetSec`）→ seek 检测 → 状态变化（`status_update`、`playback_pause` / `playback_resume`）→ 行号变化时发 `lyric_update` → `EmitPositionSample`。

### 1.2 各环节与实测的对应

| 环节 | 行为 | 实测 |
|---|---|---|
| 换歌分支 | 以 DOM 歌名与歌手变化判换歌，时钟置零且不在走。其后是阻塞操作：`ForceFetchLyricsInRedux`、等 300ms、重取 `Extract`（取不到 Redux ID 再等 500ms 重取，仍取不到联网 `lyric.SearchSongID`）、`FetchCoverViaCDP`、`FetchLyricsViaCDP`。随 `all_lyrics` 发出的位置为 0。分支结束后，同一拍的「更新时钟」才让时钟由 0 起走 | 落后量 = 分支耗时 − 起播延迟。分支 459～696ms，起播延迟 186～451ms，两者都不固定：常态 13 首的读数在 0.20～0.40s 之间，起播延迟最长的一首只有 0.10～0.12s |
| 暂停 | 读到 `PlayingState != 2` 的那一拍冻结，发 `playback_pause` | 状态翻转之后 DOM 进度还走了约 0.5s。恢复后读数 0.73～0.88s，保持到曲终 |
| 恢复 | 读到 2 的那一拍从冻结值起走，发 `playback_resume`；同一拍判了 seek 则不重复发（AGENTS §3.2） | 同上 |
| seek 检测 | 条件：`DomTimeSec >= 0`、时钟在走、距换歌超过 500ms。`DomTimeSec − 时钟` 小于 −1.0 或大于 1.5 时，把时钟置为 `DomTimeSec` 并发 `playback_resume` | 时钟落在整秒上，真实位置在该秒内任意处，其后落后 0～1s。时钟超前时在下一个整秒之前触发回跳：附着后开播一例，前跳 0.00 → 16.00，1.06s 后回跳 17.06 → 16.00 |
| `EmitPositionSample` | 在播且本曲 `all_lyrics` 已发出时每拍调用，每 5 秒发一条，传 `clock.GetCurrent()` | 时钟是纯墙钟，与服务端外推同式，现在没有校准作用（调用点注释所记） |

### 1.3 服务端怎样用位置

均在 `server/server.go`。

- 对外事件原样转发（`NotifySubscribers`），前端拿到的 `position` 就是时钟的读数。对外约定（`doc/openapi.yaml`、`doc/API_RESPONSE_EXAMPLES.md` 的「时间插值」）：前端在 `all_lyrics`、`lyric_update` 上校正锚点，收到 `playback_resume` 以其 `position` 重新落锚，收到 `playback_pause` 停止插值。
- `UpdatePlayerState` 在 `lyric_update`、`all_lyrics`、`playback_pause` / `playback_resume`、`position_sample` 到达时记下 `Position` 与到达时刻 `PositionAt`。`PlayerState.livePosition` 在状态为 playing、且最近一次采样不来自 `playback_pause` 时按墙钟外推并钳到时长，只用于连接补发（`buildInitEvents`）与 HTTP 快照（`handleAllLyrics`、`handleLyricUpdate`）。
- `position_sample` 是内部事件（`internalEvents`），只写上述位置字段，不广播。

服务端不修正位置。时钟落后多少，后端推歌词行与前端插值就晚多少。

### 1.4 读数与真实落后量

跳秒发生在上一拍与看见它的这一拍之间，所以跳秒那一刻的真实落后量 = 读数 + 0～一个轮询间隔。原始读数（实测）：

- 同一首歌里各次读数相差约 1ms；个别拍晚几毫秒到约 30ms（一例 70ms），读数相应变小。
- 4 首出现相差整 100ms 的两档（如 243 / 343）：跳秒时刻贴着轮询的拍点，较大的一档即真实落后量。其余 9 首只有一档，真实落后量在读数之上 0～100ms。
- 换歌后、恢复后的第一个跳秒，读数与其后各次一致（相差不超过 15ms）。
- 13 首常态换歌的较大读数为 233～399ms，均值 302ms。按前两条估计，真实落后量的均值约 0.34s（推断，不确定度约 ±0.03s），范围约 0.23～0.46s。
- 默认 `cloudmusicv3-offset: 500`（`config` 的 `defaultConfigContent`）是带着这个落后量定的。

## 2. 观测模型

记 p(t) 为界面进度对应的连续位置：按定义，DOM 秒数跳到 N 的那一刻 p = N。对表的目标是「时钟 = p − L」，L 为目标落后量（§3.2）。真实落后量 λ = p − 时钟。

### 2.1 一拍的观测

每拍记三样：发出 `Extract` 之前的时刻 `sent`、它返回之后的时刻 `got`、`DomTimeSec`。DOM 文本是在 `sent` 与 `got` 之间读到的。

- 两个时刻都紧贴 `Extract` 取，不取在换歌分支或歌词补取之后，与 kugou、qqmusic 的 `sampleTime` 同一做法。
- 时钟的读写分两种时刻，不能合成一个。与 DOM 读数成对的读写——起走与冻结、行匹配、seek 检测里与 DOM 比的量及置位、对表、通知的限频——配 `got`，不配「用到它时」的时刻：否则本拍里阻塞调用的耗时会被算成时钟与界面进度的偏差。对外事件的位置与位置采样取**发出那一刻**的时钟读数：下游按事件到达的时刻落锚（§1.3），而 `got` 与发出之间可以隔着阻塞调用（Redux 歌词晚到时读翻译歌词的那次同步 CDP 调用），带 `got` 时刻的读数会让前端与服务端缓存多落后一个调用耗时，直到下一条带位置的事件。没有阻塞调用的拍上两个时刻只差微秒。
- `sent` 与 `got` 取两个时刻而不是一个：`Extract` 的往返耗时没有量过。只取返回时刻时，上一拍读 DOM 之后、返回之前发生的跳秒会落在算出的区间之外。

### 2.2 一拍可用的条件

全部成立才可用；不可用的拍同时把上一拍忘掉，所以一次跳秒要相邻两拍都可用。

| 条件 | 理由 |
|---|---|
| `DomTimeSec >= 0` | 读不到进度 |
| 时钟在走（本拍读到在播） | 暂停后 DOM 进度还会走约 0.5s（实测一例在暂停期间由 0 跳到 1），那时时钟已冻结，不能跟 |
| 不是换歌那一拍 | 这一拍的 `data` 可能已被分支里重取的读数替换，与 `sent` / `got` 不配对 |
| 距换歌超过 500ms | 沿用 seek 检测已有的抑制，等 DOM 进度换成新歌的。分支自身耗时在 459ms 以上，18 次换歌没有一次在分支之后还读到上一首的进度（否则会报前跳）。真读到时，上一首的进度通常远大于新歌的时钟，本拍会判 seek，落入下一条 |
| 本拍没有判 seek | 时钟刚被置成整秒值；拖动之后头几百毫秒 DOM 的行为也没有量过（§10.2） |

### 2.3 可信的跳秒

本拍与上一拍都可用，且本拍秒数恰为上一拍加 1。跳秒发生在上一拍的 `sent` 之后、本拍的 `got` 之前。记跨度 w = `got` − 上一拍的 `sent`，本拍往返耗时 r = `got` − `sent`，则 `got` 时刻

> p ∈ [D, D + u]，u = min(w, 1 + r)，D 为本拍秒数。

- 下界：页面读 DOM 时已显示 D，其后 p 不减。
- 上界的第一项：跳秒发生在上一拍的 `sent` 之后，到 `got` 至多过了 w。
- 上界的第二项：页面读到 D 的那一刻 p 不到 D + 1，这一刻不早于 `sent`，到 `got` 至多再过 r。「不到 D + 1」只在读 DOM 的那一刻成立，不能直接用在 `got` 时刻：`Extract` 返回得晚时，`got` 时刻的 p 可以超过 D + 1。轮询间隔不足 1s 时 w 小于 1 + r，起作用的是第一项。
- 这个区间不依赖「两拍之间一直按墙钟推进」：其间短暂停顿只会让 p 更靠近 D。唯一的例外是恰好落进下一秒的小幅前跳（秒数加 1 而 p 不在 D 附近），下一次跳秒即纠正。
- 秒数不变、回退或一次加 2 以上的都不是跳秒，不处理（后两种交给 seek 检测）。

### 2.4 跨度与轮询间隔

不设跨度上限，区间宽度 u 随 w 变宽，校准自动变弱：

| 轮询间隔 | u | 校准后 λ 的范围（§3.3） |
|---|---|---|
| 100ms（默认） | 约 0.1s 加往返耗时 | L ± 0.1s |
| 250ms | 约 0.25s | L ± 0.25s |
| 1000ms | 约 1s 加往返耗时 | 只纠正 1s 以上的偏差，与现状相当 |
| 2000ms | 每拍加 2，没有跳秒 | 不校准，同现状 |

循环被拖住（`Extract` 出错的拍、Redux 歌词补取里的 CDP 调用）或 `Extract` 自身返回得晚时，w 与 r 相应变大，处理相同。

### 2.5 模型之外的误差

- `Extract` 往返耗时：计入 w 与 r，不另作假设；数值回归时量（§10.2）。
- DOM 文本晚于真实位置更新：固定的部分已含在 L 里（L 由同样条件下的读数定出），抖动实测约 1ms。
- 网易云窗口最小化、被遮挡或泊在屏外时跳秒时刻是否不变，没有量过。`watchdog.LaunchFlags` 带着关闭后台定时器节流与渲染降级的启动参数，按理不变（推断）；列入回归（§10.2）。

## 3. 校准策略

### 3.1 规则

在每个可信的跳秒上，把 `got` 时刻的时钟夹进 [D − L, D − L + u]（u 见 §2.3）：

- 在区间内：不动。
- 低于下界（时钟落后过多）：置为下界。
- 高于上界（时钟超前）：置为上界；行匹配另用一个不回退的读数（§3.4）。

换歌、暂停恢复、跳转之后不另设规则：三者都只是让 λ 偏出区间，下一个可信的跳秒把它夹回。校准改动了时钟而前端尚不知道的量达到门槛时，另发一条 `playback_resume`（§5）。

### 3.2 目标落后量 L = 0.30s

- 需要纠正的主要情形（暂停恢复、分支偏慢、多数跳转）是时钟落后过多，被夹到下界，此后 λ = L + δ，δ 是跳秒到 `got` 的间隔（0～u）。默认轮询下为 0.30～0.40s，中值 0.35s，与常态下真实落后量的均值（约 0.34s，§1.4）一致。按读数说：校准那一拍的读数恰为 300ms，实测较大读数的均值是 302ms。
- 常态换歌：13 首里 7 首的读数在 200～300ms 之内，不动；6 首大于 300ms，提前 9～99ms。常态的均值因此提前约 0.02s，小于 L 自身的不确定度（约 ±0.03s）。
- L 不是物理量：DOM 跳秒与出声的先后没有量过。它只表示「保持现有默认偏移下的观感」。

### 3.3 不会来回校

可信的跳秒上 p = D + δ，0 ≤ δ ≤ u（§2.3），夹取等价于把 λ 夹进 [L + δ − u, L + δ]。这个区间恒含 L，所以每次夹取都让 λ 朝 L 移动且不越过 L，|λ − L| 只减不增；轮询相位的变化只改变 δ，不会把 λ 推离 L。论证只用到 0 ≤ δ ≤ u，与 u 的具体式子无关；上界若封顶在 D + 1 则 δ 可以大于 u，区间不再含 L，`Extract` 返回得晚时会把正确的时钟推离 L（§6 的用例）。由此：

- 任意一次夹取之后 λ ∈ [L − u, L + u]；从落后一侧夹回的在 [L, L + u]。
- 一次夹取的量不超过夹取前的 |λ − L|。λ 已在 [L − u, L + u] 之内时，其后由相位变化引起的夹取量不超过 u。
- 容差就是区间自身的宽度 u，不另设常量，它恒不小于相位抖动。
- 必须夹到最近的边界。改为置到区间中点时，δ 在 0 与接近 u 之间交替（实测有 4 首出现这样的两档相位）会使 λ 在 L − u/2 与 L + u/2 之间来回。

### 3.4 一次改多少

- 向前（时钟落后过多）：直接置为下界，不限幅、不渐进。超过 1.5s 的偏差在此之前已由 seek 检测处理；行匹配取「不晚于当前时间的最后一行」，向前跳直接落到该显示的那一行。
- 向后（时钟超前）：直接回拨到上界。回拨量在 λ 不为负时不超过 L（0.3s）；常态下实测只有一首需要，不到 0.1s（§4.1）。
- 行号不因回拨而回退：回拨会让位置倒退，倒退跨过行边界时 `runSession` 的行匹配（行号与上次不同即发）会把上一行再推一次、片刻后又推回当前行。为此时钟另记一个**行匹配下限**：回拨时记下回拨前行匹配所用的位置，行匹配取「时钟读数与下限的较大者」。时钟走过下限之后两者相同。seek 检测置位与换歌时清掉下限（跳转后行号本就该跟着位置走）。
- 时钟只有一条时间线。除行匹配之外，凡用到位置的地方都取时钟读数，即校准后的值；读数取在哪个时刻按 §2.1 分两种：

| `runSession` 里用到位置的地方 | 取 |
|---|---|
| 行匹配（`currentTime`） | `got` 时刻的时钟读数与行匹配下限的较大者，再加 offset |
| 行号变化时的 `lyric_update` | 发出那一刻的时钟读数 |
| 状态变化段的 `playback_pause` / `playback_resume` | 发出那一刻的时钟读数 |
| seek 检测与 DOM 比较的量 | `got` 时刻的时钟读数 |
| seek 检测发的 `playback_resume` | 发出那一刻的时钟读数 |
| Redux 歌词晚到、超时兜底的 `all_lyrics` / `lyric_update` | 发出那一刻的时钟读数（发在对表之后，§5.2） |
| 由校准触发的 `playback_resume`（§5.3） | 发出那一刻的时钟读数 |
| `EmitPositionSample` | 发出那一刻的时钟读数，时刻与位置成对取 |
| 在播转非在播时冻结 | `got` 时刻的时钟读数；下限保留 |

  对外位置因此始终在校准后的时间线上，后发的事件不会把前端锚回旧的时间线。冻结在时钟读数而不是下限：`playback_pause` 的位置要与其它事件同一条线；恢复后行匹配仍取较大者，行号不回退。seek 检测用时钟读数：它是对 p − L 的最好估计，拿下限去比会把回拨量算成偏差。
- 做法：`baseRealClock` 的读数改经 `player.LivePosition` 按给定时刻取（一条时间线，可直接复用），另加下限一个字段与取较大者的读数方法。

### 3.5 与 seek 检测的关系

- seek 检测保留，门槛不改。它每拍都比，是粗的界：λ < 0 时在下一个整秒之前触发回跳，λ > 1.5s 时触发前跳。对表只在跳秒上比，是细的界。
- 顺序：seek 检测在前，对表在后，判了 seek 的那一拍不对表。行匹配在两者之前已算好，校准后的时钟从下一拍起进入行匹配，晚至多一个轮询间隔，与 seek 相同。
- 校准不会触发 seek 检测：它只让 λ 朝 0.30s 移动且不越过，距回跳的触发线（λ < 0）0.3s，距前跳的（λ > 1.5s）1.2s。
- 现有的两种后果仍会出现，但由下一个跳秒收掉：回跳 / 前跳之后落后 0～1s；时钟超前（跳转或恢复后 DOM 迟迟不走）时误报一次回跳。

### 3.6 暂停与恢复

- 暂停中的拍不可用，不跟 DOM 的渐隐。`playback_pause` 的位置仍比界面停下的位置早约 0.5s（发出时渐隐尚未走完），本设计不改。
- 恢复那一拍时钟从冻结值起走，λ 比暂停前多约 0.5s，恢复后的第一个可信跳秒夹回，DOM 立即起走时在恢复后 1s 多一点之内。恢复后 DOM 迟迟不走时时钟会追近甚至超前，同样由跳秒处理。

### 3.7 单曲循环、曲终、时长

- 单曲循环：歌名不变，不进换歌分支。DOM 回到 0 时由回跳检测置 0（现有行为），其后第一个跳秒对表（推断）。
- 曲终自动换歌走换歌分支；播完停住转为非在播，冻结。
- 时长：不加钳制。校准只把时钟拉向 DOM 秒数附近，不会把它推过时长；`progress` 已由 `ClampProgress` 钳住。

## 4. 各情形代入

均按默认轮询（u 约 0.1s）、L = 0.30s。按读数说，规则是：读数大于 300ms 时向前拨到 300ms，小于 200ms 时回拨到 200ms，其间不动。「事件」列指由校准触发的 `playback_resume`（未告知量达到 0.2s，§5）；校准的同一拍或其后若先有 `lyric_update` 等带位置的事件，位置由它带到，不另发。

## 5. 事件

不新增事件类型。校准改动了时钟而前端尚不知道的量达到门槛时发一条 `playback_resume`，不到门槛的不发；区间内不动的本来就没有可发的。

### 5.1 为什么要发

后端自己推的歌词行从下一拍起按校准后的时钟，不依赖事件。但前端在带位置的对外事件上落锚、其间按墙钟推进（§1.3），而 `position_sample` 不广播。校准之后若迟迟没有 `lyric_update`（长间奏、当前行很长、无歌词的歌），前端收不到新位置。例：无歌词的歌暂停后恢复，恢复那一拍发 `playback_resume`（位置 30.0，界面实际在 30.8）；0.2s 后可信的跳秒把时钟拨到 30.7；此后后端落后 0.3s，前端仍落后 0.8s，直到曲终。不发事件，「恢复后、跳转后落后量一致」在前端一侧没有兑现。

### 5.2 未告知量与门槛

记一个带符号的**未告知量**：校准把时钟改了多少、而前端还不知道。

- 每次校准把改动量（向前为正、回拨为负）加进去。
- 任何带位置的对外事件发出时清零：前端据它落锚到当时的时钟读数，此前的改动都已包含在内。`runSession` 里这样的事件有：换歌分支、Redux 歌词晚到、超时兜底发的 `all_lyrics` 与紧随的 `index: -1` 的 `lyric_update`；seek 检测发的 `playback_resume`；状态变化段的 `playback_pause` / `playback_resume`；行号变化时的 `lyric_update`。换歌时一并清零。`position_sample` 不广播，不清零。
- 「此前的改动都已包含在内」要求事件发在本拍的对表之后，或所在的拍不对表。Redux 歌词晚到与超时兜底的两处为此推迟到对表之后、状态变化之前才发出：状态（歌词、是否纯音乐、时长）仍在分支里就地更新，本拍的行匹配要用；位置在发出时才取。换歌分支与 seek 检测的两处排在对表之前，那两种拍不可用（§2.2），本拍不对表。
- 绝对值达到 0.2s 即该通知。

0.2s 的依据：默认轮询下常态换歌的微调，单首累计不超过 99ms（§4.1），留一倍余量，常态下不发；需要通知的校准（暂停恢复后 0.43～0.48s）远在其上；与 NTP 的步进门槛同量级（§8）。门槛不随 u 变：按累计量判，结论就是「前端与后端的位置相差不到 0.2s」，与单次校准的大小、轮询间隔都无关。轮询间隔配大后，相位变化引起的校准也可能累计到 0.2s，那同样是后端位置真的变了这么多，照发，由 §5.4 的限频约束条数。

### 5.3 时机与位置

每拍末尾（行号变化的 `lyric_update` 之后）检查一次，不限于有跳秒的拍：在播、未告知量达到门槛、且距上一次由校准触发的通知不短于限频间隔，就发一条 `playback_resume`，位置取发出那一刻的时钟读数（§2.1），随后清零。

- 时钟只有一条时间线（§3.4），向前与回拨的通知取法相同，都与同一时刻别的对外事件的位置一致。
- 与同拍去重（AGENTS §3.2）：一拍之内带位置的对外事件分两类。发在本拍对表之后的（补发的 `all_lyrics` 与紧随的 `index: -1` 的 `lyric_update`、状态变化段的 `playback_pause` / `playback_resume`、行号变化的 `lyric_update`）：位置已含本拍的校准，发出时未告知量清零，拍末的检查不会再发。发在对表之前的只有换歌分支与 seek 检测的两处：那两种拍不对表，清零之后未告知量不再增加。所以由校准触发的通知不与任何带位置的事件同拍，也就不存在先后顺序的问题；即便顺序不同，各事件的位置同在一条线上，前端最终的锚点相同。补发的歌词若留在对表之前发出，这个论证不成立：它清零之后本拍的校准又记一笔，达到门槛时拍末另发一条，同一拍先后落锚两次（§6 的用例）。

### 5.4 限频

两次由校准触发的通知之间至少隔 `player.PositionSampleInterval`（5 秒）。间隔未到时**顺延，不丢弃**：未告知量照常累计，间隔一到、仍达门槛就发；其间若有带位置的对外事件，未告知量清零，不再补发。

- 取 5 秒：与服务端缓存的校准节拍相同，不新增常量。
- 条数：任意时长 T 内不超过 T / 5s + 1 条，前提不成立（如窗口不在前台时跳秒时刻不稳，§2.5）时也如此。
- 模型之内不丢通知：一次扰动（暂停恢复、跳转、分支偏慢）之后 |λ − L| 只减不增（§3.3），累计校准量不超过扰动造成的偏差，通常一次到位、发一条。分两步到位的（第一步的 u 因 `Extract` 返回得晚而偏大，第二步在约 1s 后，§6 的用例）第二条顺延至多 5 秒，其间前端与后端相差不到一步的量。
- 不以「一段连续可用的拍」为单位限制条数，理由见 §9.7。

### 5.5 其余

- 服务端缓存：通知到达即按它落锚（`UpdatePlayerState`）；未达门槛的校准由其后的 `lyric_update` 与至多 5 秒一条的 `position_sample` 带到。`runSession` 调 `EmitPositionSample` 处「眼下没有校准作用」的注释随实现改掉：时钟不再是纯墙钟。
- 日志：单次校准量达到 0.2s 时打一行 Info，写校准前后的位置，不受限频约束。直播时 stderr 是唯一的现场记录，跳秒时刻不稳会表现为这行反复出现。

## 6. 可离线测试的拆分

`runSession` 的轮询循环没有离线夹具。判定与时钟的写法抽成不依赖 CDP、不取当前时刻的三件，都在 `player/cloudmusic`：

```go
// domSample 一拍的观测。
type domSample struct {
	sent, got time.Time // Extract 发出之前、返回之后
	sec       int       // DomTimeSec
	playing   bool      // 时钟在走
	sameSong  bool      // 不是换歌拍，且距换歌已超过 500ms
	seeked    bool      // 本拍判了 seek
}

// domSync 记上一拍可用的观测，零值可用。
// observe 返回 got 时刻时钟应在的位置；不是可信的跳秒时原样返回 pos。
func (s *domSync) observe(cur domSample, pos float32) float32

// untold 记校准改动了时钟而前端尚不知道的量（§5.2），零值可用。
// add 记一次校准的改动量；anchored 在带位置的对外事件发出后调用，清零；
// due 报告此刻该不该发通知，为真时清零并记下时刻（限频见 §5.4）。
func (u *untold) add(delta float32)
func (u *untold) anchored()
func (u *untold) due(now time.Time) bool

// at 返回 t 时刻的时钟读数（经 player.LivePosition）；lineAt 返回行匹配用的读数，
// 即 at 与行匹配下限的较大者；adjust 把 t 时刻的读数改到 want，回拨时记下限；
// jump 供 seek 检测置位，清掉下限。
func (c *baseRealClock) at(t time.Time) float32
func (c *baseRealClock) lineAt(t time.Time) float32
func (c *baseRealClock) adjust(want float32, t time.Time)
func (c *baseRealClock) jump(pos float32, t time.Time)
```

夹取用现成的 `player.ClampFloat32`。`runSession` 里带位置的对外事件统一经一个局部函数发出，由它调 `anchored`；它们的位置经另一个局部函数取发出那一刻的时钟读数（§2.1）。

**`observe` 的表驱动用例**

- 正例：加 1 且时钟落后过多，得下界；超前，得上界；在区间内、恰在两端，原值；跨分钟（59 → 60）；上一拍的 `Extract` 耗时长（`sent` 与 `got` 相距 80ms），w 自上一拍的 `sent` 起算；相邻两拍的 `sent` 相隔 1.5s、本拍往返 5ms，上界取 D − L + 1.005。
- `Extract` 返回得晚（审查给出的时间线）：p(t) = 10.9 + t，时钟恒为 p − 0.3；上一拍 `sent` = 0、`got` = 0.005、秒数 10；本拍 `sent` = 0.1 时页面读到 11，`got` = 1.3。此时时钟 11.9，u = min(1.3, 2.2) = 1.3，区间 [10.7, 12.0]，原值。上界封顶在 D + 1 时区间是 [10.7, 11.7]，会错误回拨 0.2s。
- 反例，一律原样返回：秒数不变；加 2；减 1；会话的第一拍；上一拍或本拍 `sec` 为 −1；上一拍或本拍不在播（含暂停期间 DOM 由 0 跳到 1）；恢复后的第一拍；上一拍或本拍是换歌拍或距换歌不足 500ms；上一拍或本拍判了 seek；隔着一个不可用拍的加 1（可用、不可用、可用）；本拍的 `got` 不晚于上一拍的 `sent`。

**`untold` 与时钟的用例**

- `untold`：累计 0.19s 不到、0.2s 到；+0.15 再 −0.15 相消，不到；`anchored` 之后清零；`due` 为真之后清零；第一次无须等间隔；距上一次不足 5 秒时 `due` 为假而量保留，满 5 秒即真；顺延期间 `anchored`，间隔到了也为假。
- 时钟：`at` 按给定时刻取；向前 `adjust` 不设下限；回拨之后 `at` 取回拨后的值，`lineAt` 取回拨前的值、直到 `at` 走过它；`jump` 清下限；回拨后冻结取 `at`，恢复后 `lineAt` 仍不小于冻结前的。

**回放用例**：假时间线上 p 按墙钟推进、每 100ms 一拍，按 `runSession` 一拍之内的顺序（行匹配 → seek 检测 → 对表 → 本拍补发的歌词 → 状态变化 → 行号变化的 `lyric_update` → 通知检查 → 位置采样）复述，不经真实的循环；一拍可带「读到 DOM 之后、发出事件之前的阻塞时长」，该拍的事件与位置采样按发出的时刻取位置；另模拟一个前端，只在带位置的对外事件上落锚（按事件发出的时刻），其间按墙钟推进，`position_sample` 不可见。

- §4.1 各首歌的初始落后量与相位，断言表中的校准后读数与事件一栏。
- 相位在 0 与 95ms 之间交替 120 秒：总调整量不超过初始的 |λ − L|，收敛后不再调整，不发通知。
- 轮询 250、1000、2000ms：结果同 §2.4。
- 无歌词的歌、长间奏（下一条 `lyric_update` 在 20s 之后）各一条，暂停时时钟早冻结 0.5s：恢复后 1.2s 之内后端与前端的落后量都回到 [L, L + u]，前端此前约为 0.8s。
- 常态换歌的微调（§4.1 前四行）：不发通知，前端与后端相差不到 0.2s。
- **u 由宽变窄（审查给出的时间线）**：一直在播，p(t) = 10.9 + t，时钟落后 0.88s。上一拍 `sent` = 0、`got` = 0.005、秒数 10；本拍 `sent` = 0.1 读到 11、`got` = 0.32，u = 0.32，时钟 10.34 拨到 10.70，发通知，此后落后 0.52s。t = 1.1 时秒数 12、u = 0.1，时钟约 11.485 拨到 11.70，未告知量 0.215s 达门槛而距上一条不足 5 秒，顺延；t = 5.32 发出。断言：后端在 t = 1.1 之后落后 0.30s；两条通知都发出；第二条之后前端的落后量在 [L, L + u]，顺延期间前端与后端相差 0.215s。
- 顺延期间遇到 `lyric_update`：未告知量清零，间隔到了也不再补发，前端已在后端的时间线上。
- 跳秒时刻不稳（无歌词的歌，迟到 0.3s 与准时的跳秒交替 60 秒）：由校准触发的通知不超过 13 条（60s / 5s + 1）。
- **校准恰逢行边界（审查给出的时间线）**：seek 之后一直在播，p(t) = t，时钟也为 t；offset 0.5s，下一行的显示边界 1.50。上一拍 `sent` = 0.95、`got` = 0.955、秒数 0；本拍 `sent` = 1.05、`got` = 1.055、秒数 1，u = 0.105，上界 0.805。本拍行匹配时间 1.555，已选中新行；时钟 1.055 回拨到 0.805，下限记 1.055，未告知量 −0.25s；随后发 `lyric_update`，位置 0.805，未告知量清零。断言：本拍对外只有这一条 `lyric_update`，不另发 `playback_resume`；前端锚在 0.805 的时间线上，落后量在 [L − u, L]；其后各拍行号不回退。行边界不在这一拍的变体：本拍末尾发 `playback_resume`，位置 0.805。
- 回拨之后、时钟走过下限之前暂停：`playback_pause` 的位置是时钟读数（回拨后的线）；恢复后行号不回退。
- 回拨之后、时钟走过下限之前到点的 `position_sample`：位置是时钟读数。
- **补词阻塞之后的位置（审查给出的时间线）**：一直在播，p(t) = 8.99 + t，时钟 = p − 0.30。上一拍 `sent` = 1.900、`got` = 1.902、秒数 10；本拍 `sent` = 2.000、`got` = 2.002、秒数 10（不是跳秒），时钟读数 10.692；本拍补到歌词（显示边界 5 秒与 60 秒），读翻译歌词的调用阻塞到 3.002 才发出。断言：3.002 发出的 `all_lyrics`、`lyric_update` 与 `position_sample` 位置都是 11.692；此后前端与后端同一条线，不多落后 1 秒。
- **补发歌词与校准同拍（审查给出的时间线）**：上一拍 `sent` = 20.000、`got` = 20.002、秒数 10；本拍 `sent` = 20.100、`got` = 20.102、秒数 11，对表前时钟 10.30，拨到 10.70；两拍都可用，没有 seek，此前没有发过通知；本拍补发的是只有提示语的那种（`all_lyrics` 加 `index: -1` 的 `lyric_update`）。断言：本拍对外只有这两条，位置都是 10.70；本拍及其后没有由校准触发的 `playback_resume`；前端锚在校准后的时间线上。另一组在同一拍加 1 秒的阻塞：两条在 21.102 发出，位置 11.70。
- 补发歌词的那一拍没有校准、没有阻塞（只有提示语、补到歌词各一组）：位置就是时钟读数，时钟不动。顺延期间补发歌词：顺延的那一笔由它带到，间隔到了不再补发。

**计划注入的变异**（各自须有用例变红）：

- 判定：去掉「恰为加 1」；允许加 2；不可用的拍不忘掉上一拍（四个条件各一）；w 改自上一拍的 `got` 起算；上界封顶在 D + 1（不加本拍的往返耗时）；上界去掉 w 一项；上下界对调；L 取反；夹到区间中点；先记本拍再比较。上界去掉 1 + r 一项不算缺陷：它仍是成立的界，只是更松，且只在轮询间隔不小于 1s 时有差别。
- 时钟：`at` 改回 `time.Since` 相加；回拨不记下限；行匹配不取下限；`jump` 不清下限；冻结取 `lineAt`；某一处对外位置取 `lineAt`（行号变化的 `lyric_update`、`playback_pause`、通知、`position_sample` 各一）；seek 检测拿 `lineAt` 与 DOM 比。
- 通知：从不发；去掉门槛；改动量取绝对值累加；`anchored` 不清零；`due` 为真之后不清零；去掉限频；顺延写成丢弃（间隔未到时清零）。
- 两个时刻与补发的时机（注入在回放里）：对外位置取 `got` 时刻的读数（全部，以及只有行号变化的 `lyric_update`、补发的 `all_lyrics`、`position_sample` 各一）；补发放回对表之前；补发留在对表之后而位置在对表之前取好；补发的事件不清未告知量。

**清零点**：带位置的对外事件是否都经那个局部函数发出，离线回放守不住（回放自己决定何时调 `anchored`）。实现时加一条 AST 门禁，体例同 `player/lyricupdate_lint_test.go`：本包里 `all_lyrics`、`lyric_update`、`playback_pause`、`playback_resume` 四种事件的 `Emit` 只许出现在该局部函数内，某一处绕过即红；做不成则记进「靠人守」。

**只能靠人守**（实现时记进 AGENTS §4 的「靠人守」表）：`sent` / `got` 紧贴 `Extract` 取；两种时刻各配什么（§2.1：与 DOM 读数成对的读写配 `got`，对外事件的位置与位置采样取发出那一刻的读数）；三个标志取对量；一拍之内的顺序（对表在 seek 检测之后，补发的歌词事件在对表之后、状态变化之前，通知检查在行号变化的 `lyric_update` 之后）；行匹配取 `lineAt`、其余各处取 `at`（§3.4 的表）；seek 检测经 `jump` 置位。L、门槛与限频间隔的取值来自真机，离线测试只守逻辑。

## 7. 仓库内的先例

`player/applemusic/applemusic.go` 的 `clock`（AGENTS §7.8 第 2 条）同样是「整秒读数 → 连续位置」：位置 = 锚点 + 墙钟流逝，读数每跳一次把估计夹回 `[raw+flipLagMin, raw+flipLagMax+距上次读数]`，在范围内不动。

**沿用**

- 夹进区间而不是每跳落锚；上界加上距上一次读数的时间。本设计的规则即此式，带宽为 0（见下）。
- 事件分两档：`clock.observe` 把偏出范围不到 `seekJumpSec` 的估计静默夹回（返回 `evNone`），超过的才返回 `evSeek`、发 `playback_resume`。本设计同样是小的校准不发、大的发，只是门槛不同（§5.2）；在区间内不动的，两边都无事可发。
- 时钟按传入的时刻读写，不在内部取当前时刻。

**不照搬**

| applemusic | 网易云 | 结果 |
|---|---|---|
| 读数约每 256ms 刷新一次，跳变时刻相对真实位置有 0.38～0.63s 的带 | DOM 跳秒时刻的抖动约 1ms | `flipLagMin` 与 `flipLagMax` 合为一个 L，区间宽度只剩 w |
| 读数滞后于出声，时钟要比读数靠前；滞后是以出声为准量出的 | 时钟要比 DOM 靠后 L；L 是为保持现有观感而留的，没有以出声为准的测量 | L 不能当作物理常量引用 |
| 没有播放态，暂停、恢复、跳转都由读数推断（`pauseThreshold`、`resumeConfirm`、`jumpHold`、`seekJumpSec`、`seekLag`） | 有 Redux 的 `playingState`，seek 检测已有 | 这些都不搬 |
| 每 50ms 读 24 字节内存，耗时可忽略，取一个时刻 | 每 100ms 一次 CDP 往返，耗时未量 | 取 `sent`、`got` 两个时刻 |
| `clock.live` 不让位置越过 `lastRaw+1+flipLagMax` | — | 对应「每拍上界」，暂不采用（§9.5） |
| 向后夹时位置回拨；行号只往前走（`nextLine`） | 行号与上次不同即发 | 同样回拨，行匹配另取不回退的读数（§3.4），作用同 `nextLine` |

类型不复用：`clock` 是 applemusic 包内的未导出类型，与由读数推断播放态的逻辑写在一起；抽到公共包要动它的全部时钟用例，换来的只是十来行夹取。复用的是 `player.ClampFloat32` 与 `player.LivePosition`。

sodamusic 的 `lastRawSec`（AGENTS §7.7.1）是同一思路的另一例：只在读数变化的那一拍落锚。它的读数是采样瞬间的真实位置，可以直接落锚到读数；网易云的是整秒值，可用的只有变化的时刻。

## 8. 外部参考

- **NTP**（[RFC 5905 §11.3](https://www.rfc-editor.org/rfc/rfc5905.txt)）：偏移小于步进门槛 STEPT（0.125s）时只渐调，超过且持续到 stepout 时限之后才直接置时钟。对应本设计：小的偏差不动（区间内）或校准而不声张，大的才通知下游；发事件的门槛 0.2s（§5.2）取在同一量级。
- **MPRIS**（[Player 接口](https://specifications.freedesktop.org/mpris/latest/Player_Interface.html)）：`Position` 变化不发 `PropertiesChanged`，客户端按 `Rate` 自行推进；位置的变化与当前播放态不一致时发 `Seeked`，开始播放与换曲时不必发。本项目的 `playback_resume` 相当于 `Seeked`。客户端自行推进的前提是对外给出的位置连续；达到门槛的校准使它不连续，按同一约定要通知（§5.1），不到门槛的相当于 `Position` 的日常推进，不逐次通知。
- **Taskbar-Lyrics**（BetterNCM 插件，[lyrics.js](https://github.com/mo-jinran/Taskbar-Lyrics/blob/main/plugin/js/src/lyrics.js)）：在网易云页面里用 `channel.registerCall("audioplayer.onPlayProgress", …)` 接原生层的进度回调，取第二个参数作当前位置（秒，带小数），每次回调按它选歌词行，不自行计时。
- **NeteaseHookSDK**（[DESIGN.md](https://github.com/lgnorant-lu/NeteaseHookSDK/blob/main/docs/DESIGN.md)）：经 9222 端口用 CDP `Runtime.evaluate` 注入脚本，同样挂 `audioplayer.onPlayProgress`。

后两条说明网易云页面里有比 DOM 整秒值更细的进度来源，开源工具的做法是直接取它，而不是对粗粒度进度对时。本设计不走这条路的理由见 §9.4。有限的检索里没有查到「只拿整秒进度、靠跳变时刻对时」的开源歌词工具。

## 9. 考虑过而不采用的方案

### 9.1 按换歌分支耗时补偿

上一版实现（未合入）：位置起点 = 分支耗时 − 520ms。它的前提「新歌进度在歌名变化后约 0.24s 起走」被第二次实测否定：起播延迟为 186～451ms，且与分支耗时同向变化，原先的落后量里两者相消。只去掉分支耗时一侧，分支偏慢的两首反而偏早（331 → 155ms、115 → 69ms）。它针对的慢路径在 18 次换歌里没有出现，也不覆盖暂停恢复与跳转。

### 9.2 对表但不保留落后量

L 取 0：整体提前约 0.3s，默认 `cloudmusicv3-offset: 500` 须重调，而现有的 config.yml 里都写着它。已由用户否决。另外 L 为 0 时 λ 的下沿为负，贴着回跳的触发线。

### 9.3 每段只校一次，首个跳秒直接置位

换歌、恢复、跳转之后的第一个跳秒把时钟置到区间中点，之后不再动。常态下各首歌的散布可由 ±0.1s 收到 ±0.05s。不采用：要多记「这一段是否已校」并在三处复位；首个跳秒若有偏差，整段不再纠正；±0.1s 与 ±0.05s 的差别看不出来。夹取的结果不依赖此前是否校过，偏了能在下一个跳秒收回。

### 9.4 更细的进度来源

- Redux 的 `playing.playingLyricLineNumber`：`cdp` 包的 `jsPayload` 一直在取它并换算成 `ExtractionData.CurrentProgress`（当前行的时间），自首个网易云提交 `fa59084` 起就在载荷里，`runSession` 从未使用。它只在行切换时变化，依赖 `async:lyric` 分片（`jsPayload` 的注释记为只在歌词页打开时才有），无歌词的歌没有，相对出声的早晚也没有量过。仓库内（`cdp` 包、`tools/cdpexplore`、AGENTS.md、git 历史）没有别的记载。
- 原生回调 `audioplayer.onPlayProgress`（§8）：给出带小数的当前位置。要经 CDP 往页面里挂 `channel.registerCall`，会不会顶掉网易云自己的处理函数、各版本是否一致都不清楚，须在真机上探测，且属于往别人的进程里加东西（AGENTS §0 第 1 条）。它若可用，对表与落后量都不再需要；已另立 issue #82 评估，不在本设计之内（§11）。
- 在 `jsPayload` 里带回页面内的时间戳，代替 `sent` / `got`：要改 `cdp` 包，并混用页面的墙钟与 Go 的单调时钟。往返耗时计入 w 已经够用。

### 9.5 每拍上界

时钟在任何一拍都不越过 D + 1 + r − L（对应 applemusic `clock.live` 的上限），可以把「时钟超前 → 误报回跳」换成让时钟停在上限。恢复、跳转之后 DOM 会停多久没有数据，先不加（§12）。

### 9.6 向后校准时停走，不回拨

前两稿的做法：时钟不回拨，停在原处直到上界追上来，通知里带校准后的时间线。这样停走期间有两条时间线，每一处对外位置都得指定取哪一条；漏掉一处（如同一拍里行号变化的 `lyric_update`），前端就被锚回旧的时间线。改为只留一条时间线、行匹配另取下限（§3.4）：对外位置无须逐处指定，行号同样不回退。

### 9.7 「每段连续可用的拍至多发一条通知」

上一稿用它防刷事件。它把第一次校准的 u 当成了其后各次的 u：第一次校准恰逢 `Extract` 返回得晚、u 偏大时落后量只收到 L + u 以内，下一个跳秒还要再校一次，这第二次的通知会被压掉。改为按未告知量判、按时间限频并顺延（§5.4）。

## 10. 验证计划

### 10.1 离线

§6 的用例与变异；`gofmt -l .`、`go vet ./player/...`、`go test -count=1 ./player/...`。离线测试守不住 L 的取值与 §2.5 的各条。

### 10.2 真机回归

探针构建（只加日志，不提交）。每个可信的跳秒打印：秒数、w、`Extract` 往返耗时（`got − sent`）、校准前读数、动作（不动 / 向前多少 / 回拨多少）、校准后读数、未告知量；由校准触发的通知另打一行。seek、暂停、恢复沿用现有日志。读数的预期按默认轮询。

| 情形 | 预期 |
|---|---|
| 常态连续切 10 首以上 | 每首第一个跳秒之后读数都在 200～300ms；单次向前不超过约 0.1s；同一首歌稳定之后不再有动作；`/cloudmusicv3/ws` 上没有由校准触发的 `playback_resume` |
| 暂停 2s 以上再恢复，同一首歌重复 3 次；有歌词的歌与无歌词的歌各做一遍 | 恢复后第一个跳秒的校准前读数约 700～900ms，向前 0.4～0.6s，其后读数 200～300ms；多次暂停不累积。每次恢复在 `/cloudmusicv3/ws` 上是两条 `playback_resume`：恢复那一拍一条，约 1s 内校准一条，后者的位置比按前者推算的多 0.4～0.6s（校准那一拍恰好换行时，由那条 `lyric_update` 代替）。5 秒内连做两次的，第二次的通知顺延到满 5 秒 |
| 向前、向后拖动各 3 次 | seek 日志之后的第一个可信跳秒校准，其后读数 200～300ms。另记拖动过程中与松手后 1s 内的秒数序列（是否随拖动变化、是否闪回）、回跳有没有多报 |
| 启动时附着，歌在播、歌暂停各一次 | 前跳之后的第一个可信跳秒校准，其后读数 200～300ms |
| 单曲循环一次 | 回跳之后的第一个跳秒校准 |
| 网易云窗口最小化、被别的窗口盖住、泊在屏外，各播 1 分钟 | 读数与前台时相同，同一首歌里稳定；w 与往返耗时不变 |
| 往返耗时 | 记下分布。明显超过 20ms 时回头核对 §2.5 |
| 观感 | 默认 `cloudmusicv3-offset: 500` 下，歌词的早晚与改动前的常态一致；暂停恢复、拖动之后不再偏晚 |

issue #77 的验收条件（切歌后 `lyric_update.position` 与进度条的差值，和切歌前一首稳定播放时相当）由第一行覆盖。

**回归结果**（2026-10-09，`b2b0357` 加探针；逐项数据在 issue #77 的评论）：

- 常态换歌 10 首：校准后读数 155～300ms（155 的一首当拍往返 44ms、区间随之变宽），单次校准不超过 58ms，没有由校准触发的 `playback_resume`。换歌走慢路径的 2 首（分支 1.1～1.2 秒）：读数由 690、890ms 在第一个跳秒校到 300ms，各发一条。
- 暂停后恢复 8 次（有歌词 3、无歌词 5）：校准前 867～915ms，向前 0.57～0.62s，其后 300ms，不累积；一次校准恰逢换行，由那条 `lyric_update` 带到；5 秒内连做的顺延到满 5 秒。
- 拖动 8 次、启动附着 3 次：判 seek 之后的第二个跳秒校到 200～300ms（第一个跳秒的上一拍不可用），约 1.1 秒内到位。
- 同一首歌收敛之后读数稳定在一档（±1ms）或 200 / 300ms 两档之间，最长 140 秒，看不出漂移。网易云窗口最小化期间读数不变。
- `Extract` 往返耗时常态 0～2ms，换歌那一拍 39～156ms，一次约 1.3s（页面卡顿，其间 DOM 停在 0）。
- 未测：单曲循环；窗口被遮挡、泊在屏外；Redux 歌词晚到与超时兜底的补发路径（未触发）。
- 拖动后 DOM 有时在 0.1s 内就跳秒（置位时真实位置已近下一秒），有时停住约 1 秒（8 次里 1 次，误报一次回跳，其后校回）。

## 12. 待定

1. **L 的取值。** 0.28～0.34s 都与数据相容。建议 0.30s：校准那一拍的读数与实测较大读数的均值相同，常态均值的变化约 0.02s。回归后若观感整体偏早或偏晚，只改这一个常量。
2. **通知的门槛与限频间隔。** 建议 0.2s 与 5 秒（§5.2、§5.4）。0.2s 来自实测里常态微调的最大累计量（99ms）加一倍余量；回归时若常态换歌出现由校准触发的 `playback_resume`、或暂停恢复后没有，调门槛；若分两步到位的情形常见、第二条总被顺延，缩短间隔。
3. **每拍上界（§9.5）。** 建议等回归采到恢复、拖动之后 DOM 的停留时长与回跳误报的次数再定。
4. **窗口不在前台时跳秒时刻是否不变（§2.5）。** 这是本设计的前提，只有回归能验。不成立时须先停下重议，不带着它合入；§5.4 的限频只保证那时不刷事件，不保证位置准。回归里最小化期间读数不变（§10.2 末）；被遮挡与泊在屏外未测。
