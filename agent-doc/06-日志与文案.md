## 6. 日志与文案规范

规范分三层，**别把三层混为一谈**。三层平铺成一张表时，编译期约束和代码并未照做的措辞惯例长得一模一样，读者只能整表当教条或整表无视。分层的意义就是让「违反即 bug」与「参考现状」可区分。

### 6.1 强制（违反即 bug）

| 规矩 | 为什么 | 谁在守 |
|---|---|---|
| **运行时代码必须用 `logger` 包，绝不 `fmt.Println` / `log.Printf` 直出状态**。例外见 6.2 末；音频 helper 子进程不走 logger，用标准 `log.Printf` 加 `[helper]` 前缀写 stderr，由 Manager 的 `cmd.Stderr = os.Stderr` 并入主控制台（§3.6）。 | 模块名 + 级别图标是直播中定位故障的唯一线索，裸 print 没有这两样。 | ❌ 靠人 |
| **同一事件在六个播放器里文案必须逐字一致**；不一致必须有**机制上**的理由（见 6.2），「懒得改」不是理由。 | 运营在同一屏日志里横跨六个播放器排查，措辞漂移 = 无法 grep。 | ❌ 靠人 |
| **日志里的状态值必须来自真检测，绝不写死字面量。** | 见下文。 | ❌ 靠人 |
| **一个 package 只有一个 `log` 变量**；同包多文件共用（`player/wesing/lyric/finder.go` 的包级 `var log` 声明，`reader.go`/`timer.go` 共用）。同包确需两个 → 换名（`server` 包的 `serverLog`（server.go）/ `routerLog`（router.go））。 | Go 编译期约束，不是风格偏好——同包重复声明 `log` 直接编译不过。 | ✅ 编译器 |
| **绝不在模块内自行 `log.SetFlags`**。时间戳由 `main()` 开头的 `log.SetFlags` 统一设定。 | 各模块各设 = 同一屏日志出现两种时间格式。 | ❌ 靠人 |

**「逐字：否」是断言，不是报告。**

全仓带「逐字」状态的日志现有 **17 处：15 处真检测、2 处仍写死**。格式串是英文原文（issue #61 起，§6.4），「逐字：」在英文原文里有 `per-character: `、`per-word: `、`word-by-word: ` 三种写法（见 §6.3 末），写死的两处是 `per-character: no`；中文环境下都显示「逐字：是」或「逐字：否」。检索：`git grep -n -E 'per-character: |per-word: |word-by-word: ' -- '*.go' ':!*_test.go' ':!i18n/*'` 命中 17 行（issue #61 改向后逐行核实；改向前按 `逐字：` 检索命中 21 行，其中 4 行是注释，那 4 行注释仍在）。本节初写时是「8 写死、3 真检测」——qqmusic（QRC）、kugou（KRC，`97f60d8`）、wesing（内存 `CharElement`）的逐字先后接入后都改用了真检测，见下方实证。

| 写法 | 位置 |
|---|---|
| ✅ 真检测（`detailedFlag()` / `lyricDetailedFlag()`，遍历 `TextDetailed.Words`） | `player/cloudmusic`（CDP / API / fetch 共 3 处）、`player/qqmusic`（4 处）、`player/kugou`（3 处，`97f60d8` 起）、`player/wesing`（`detailedFlag()`）、`player/sodamusic`（2 处）、`player/applemusic`（2 处：`emitAllLyrics` 与 `emitVerdict`）——**按符号找，不记行号** |
| ❌ 写死 `no`（中文环境显示「否」） | `player/cloudmusic/cloudmusic.go` 两条 Redux 分支（同文件里 `lyricDetailedFlag()` 就在手边却没用） |

后果：**就算有人把逐字接通了，日志还是会说「否」**——它不是在报告状态，是在断言状态，接线者会据此以为自己没做成、回去改一个本来就对的实现。

**这条已被三次兑现、且证明有用**：qqmusic、kugou、wesing 接通逐字时，接线者都改用了真检测（qqmusic/kugou 还在代码里留注释显式引用本节「绝不写死——AGENTS.md §6.1」），没踩坑。**尤其 wesing 那处**——本节曾断言它「确无逐字源、尚可辩护」，正是这类写死最危险的形状：把「还没去读」误当成「机制上没有」，反而拦住了接线。实测证明字级时间就在 `CharElement` 里。剩下 2 处写死是 `cloudmusic` 的两条 Redux 分支——同一文件里 `lyricDetailedFlag()` 就在手边却没用，仍是隐患。

**新增任何 `<状态>：<值>` 形态的日志，值必须来自函数调用。** 想不出怎么检测，就把这个字段从日志里删掉：不报好过报错。

### 6.2 例外（机制不同，须写明理由）

**六家的能力不一致。** 逐字六家都有源；翻译 cloudmusicv3 / qqmusic / kugou / sodamusic / applemusic 五家有，只有 wesing 无来源。**这是逐步挖出来的、不是天然分界**：kugou 一度也被归进「都无」（见 §6.1 的写死日志与下文 ①），先后两个 commit 才把它的逐字与翻译从 KRC 挖通。wesing 现在的翻译「无」同样可能只是「还没挖」，别倒果为因（下文 ①②）。以下为代码真源 + WS 录音双证：

| | `sub_text`（翻译） | `text_detailed`（逐字） | 纯音乐 |
|---|---|---|---|
| **wesing** | 无 | **有**（内存直读 `CharElement`，非 HTTP） | **情况不存在** |
| **cloudmusicv3** | **有** | **有**（YRC） | 平台返回「纯音乐，请欣赏」→ 归一为 `index:-1` |
| **qqmusic** | **有** | **有**（QRC） | API 返回零行 → `index:-1` |
| **kugou** | **有**（KRC 内嵌 `[language:]`） | **有**（KRC，`97f60d8` 起） | 同 cloudmusic（两家文案一字不差） |
| **sodamusic** | **有**（tlyric 式独立 LRC，取自 `translations.cn`，按绝对时间戳对齐——非酷狗的行号对齐） | **有**（明文 KRC，与 kugou 同格式） | 无歌词 → `index:-1`（同 cloudmusic/kugou） |
| **applemusic** | **有**（iTunes TTML `<translations>`，按 `itunes:key`（L1/L2…）与正文行配对——非行序、非时间戳） | **有（条件性）**（TTML `itunes:timing="Word"` 才有 `<span>` 逐字；Line 型无，由 `detailedFlag()` 逐曲如实反映） | 无属于当前歌的 TTML（不在内存、时长对不上、已被别的曲目认领或解析不出行，§7.8）→ `index:-1`（同 cloudmusic/kugou）；TTML 只有一行「纯音乐，请欣赏」同样按无歌词，提示随 `index:-1` 发出 |

**逐字现在六家都有源；翻译五家有（cloudmusicv3 / qqmusic / kugou / sodamusic / applemusic）、只有 wesing 无来源。** 本节几经订正，两条曾经的「过时」都已翻案：

- **kugou 逐字**（`97f60d8`）：从 `krcs.kugou.com` 拿 `fmt=krc` 解出字级时间轴。**kugou 翻译**（`447686b`）：同一份 KRC 里内嵌的 `[language:]` 标签（base64 JSON，`type=1` 中文翻译轨，按 `[start,dur]` 行号对齐，非网易云那种时间戳匹配）→ 赋进 `SubText`。二者同一次 `fmt=krc` 请求、同一次解密，白搭车。kugou 的逐字/翻译都是**条件性**的：拿不到 KRC、回落到行级 `fmt=lrc` 时 `text_detailed`/`sub_text` 都空，由 `detailedFlag()` 如实反映。
- **wesing 逐字**（内存直读）：**曾断言「机制上不成立」，实测推翻**。全民K歌是卡拉OK，字级时间就在 `CharElement` 里——`+0x04` 字起始秒、`+0x08` 字时长秒（2026-07-18 实测：首字起始 = 行时间，行内严格递增，末字终点≤下一行起点，53/53 行吻合；**跨进程重启一致**，只有模块基址随 ASLR 变、结构体内偏移全不变）。`reader.go` 的 `LoadLyrics` 此前遍历 `CharElement` 只读了文本（`+0x00`→RenderData），这两个时间字段整个略过了——不是「没有逐字源」，是「没去读」。时间轴不合法的行退回行级（`Detailed` 为空 `{}`），由 `detailedFlag()` 如实反映。
- **sodamusic 逐字**（明文 KRC）：字节的 transport 直接给**已解密的明文 KRC**（`lyrics.type==='krc'`，格式与酷狗字级完全同构 `[行起ms,行长ms]<字偏ms,字长ms,0>字`），故复用 `player/krc` 公共包解析、连解密都省。逐字是**条件性**的：`type` 非 krc / 内容为空时按无歌词处理，由 `detailedFlag()` 如实反映。KRC 解析已抽 `player/krc` 单一真源，kugou 与 sodamusic 共用（`ParsePlainKRC`）。
- **applemusic 逐字/翻译**（iTunes TTML，纯内存扫出、见 §7.8）：`itunes:timing="Word"` 的歌 `<p>` 内含 `<span begin=…>字</span>` = 逐字，`itunes:timing="Line"` 则无——**逐字对 applemusic 是「视歌曲而定」而非「拿到歌词就有」**，由 `detailedFlag()` 逐曲如实反映（2026-10-08 端到端各次真机运行的日志里，歌词加载均为「逐字：否」；Word 型占比未统计）。翻译取自 TTML 内嵌的 `<translations><translation xml:lang><text for="Lk">`，**按 `itunes:key`（L1/L2…）与正文行配对**——不按行序（与 kugou 的 `[language:]` 按行序对齐不同），也不按时间戳（与 soda/cloudmusic 不同）；该曲无译轨或某行无对应译文时该行 `sub_text` 空。

**只剩 wesing 翻译仍无来源**：`player/wesing/` 包零 HTTP，渲染内存里见过主歌词与音译两条轨（§7.5），没见过翻译轨（夹在两者之间的那条轨在实测的歌上是空的，是不是翻译轨没有验证）；它手里的 mid（`songinfo.go` 从内存 JSON 刮的）是**全民K歌曲库 mid，不是 QQ 音乐 songmid**（2026-07-18 实测：拿去 QQ `fcg_query_lyric_new` 返 `retcode=-1901`、`musicu.fcg` 返 `songID=0/qrc=0`），故走不通 QQ 那条翻译源。要上 wesing 翻译得先找到可用的外部翻译源。

#### 「没有」分两种，别混

**① 无来源 —— 还没挖出取词路径**（现只剩 **wesing 的翻译**一项）

> 这一类正在逐条被挖通：kugou 逐字（`97f60d8`，KRC）、kugou 翻译（`447686b`，KRC 内嵌 `[language:]`）、wesing 逐字（内存 `CharElement`）先后挖通——应验了本节稍后仓库所有者那句「将来挖出来了就该补上」。**只剩 wesing 翻译无来源**。

wesing 扫的是内存里**已渲染完成**的歌词：`player/wesing/lyric/reader.go` 的 `LyricLine` 是 `{Index, Time, Text, Detailed}`（`Detailed` 即逐字，`SubText` 尚无——无翻译源）。整个 `player/wesing/` 包**零 HTTP 引用**（实测 grep `net/http` 无命中）——这正是翻译无来源的根：翻译要么来自外部 API（与 zero-HTTP 设计冲突），要么内存里有翻译轨（渲染内存只有演唱词，没有）。**注意「零 HTTP」不再等于「零逐字」**：逐字来自内存字级时间，不需要 HTTP。

**但这只等于「我们目前拿不到」，不等于「平台没有」。** 仓库所有者原话：「逐字和翻译，是因为我们还没挖出来。」将来挖出来了就该补上，那不是破坏一致性，是补齐。

⚠️ **本节此前写的是「这些概念对 wesing 根本不成立」——那是把「没找到」写成了「不存在」**，正是本文档反复警告的那个动作（见 §3.0）。一个未经验证的推论被写进规范，就成了后人不再质疑的前提。

它还与 §6.1 自相矛盾：那里写着「**就算有人把逐字接通了**，日志还是会说『否』」——那句话的前提正是「逐字可以被接通」。同一份文档，两处打架，而没人发现。

（精确一点：wesing 有 mid，`lyric/songinfo.go` 从内存 JSON 里刮出来的，但它只用于 `FindCoverURL` 的内存 AOB 匹配，不用于任何取词请求。别把「有 mid」误读成「能查歌词」。）

**② 情况不存在 —— 领域约束**（wesing 的纯音乐）

wesing 是 K 歌平台，**曲库内所有歌都带词**。所以「纯音乐」这个状态对它不成立，`index:-1` 结构上永远不会发出。这不是实现限制，改不改代码都一样。

（`initSong` 里 `len(lyrics)==0` 直接返回失败、一个事件都不发——那描述的是「假如出现纯音乐会怎样」，而那个前提不成立。别把实现细节当理由写。）

> sodamusic 与 kugou 都出 KRC 逐字、但翻译机制不同：kugou 的译文内嵌在同一份 KRC 的
> `[language:]` 轨里、**按行号对齐**；sodamusic 的译文是独立的 tlyric LRC（`translations.cn`）、
> **按绝对时间戳对齐**（同 cloudmusic 的 `MergeTlyric`）。别把两者的对齐口径搞混
> （见 `player/sodamusic/translation.go` 与 `player/krc`）。
>
> **sodamusic 的时间戳对齐带 ±10ms 容差，不是精确相等——那不是放宽，是补上精度差。**
> 2026-08-08 真机实测：译轨是厘秒制（`[00:26.56]`），而 KRC 行起始是毫秒制，两者精度不同源。
> 《We Are The World》105 行**全部整 10ms 对齐**、精确相等 105/105（放宽后结果一字不变）；
> 但同日《听海》32 行的行起始是 `45519 / 53253 / 60457` 这种毫秒值，**整 10ms 对齐只占 1/32**。
> 也就是说「KRC 可以是毫秒精度」是真实形态，一旦它与厘秒译轨相遇，精确相等会**整轨静默丢译文**
> （无日志、无报错，只是 `sub_text` 全空）。现有样本里有译轨的歌恰好都整 10ms 对齐，
> 那是相关性不是保证。容差取 10 = 一个厘秒格，误配需要两行歌词起始相隔 ≤10ms，不可能。

| | 「无来源」 | 「逐字：否」写死 |
|---|---|---|
| 决定者 | 我们还没挖出那条路径 | 实现偷懒（有检测器不用） |
| 定性 | **合法现状**，但标注为待办 | **bug** |
| 该怎么办 | 写明「目前无来源」，别写成「不可能」 | 修 |

### 6.3 惯例（参考，非强制）

**这一层不是规矩，是现状快照，与代码分叉时以代码为准。** 例：连接成功的日志在 cloudmusic / kugou / sodamusic 三家的 `Start` 里逐字一致，写作 `CDP connected, monitoring playback state`（中文环境显示「CDP 连接成功，开始监听播放状态」）——CDP 是事件监听，不是轮询。把这层当强制，只会让人去改本来就对的日志。

新接播放器时**对齐代码现状**，不是对齐这张表。「现状措辞」列的是调用点上的英文原文（检索用它），中文环境下显示的是译表里对应的中文：

| 场景 | 现状措辞（英文原文） | 中文环境显示 | 覆盖 |
|---|---|---|---|
| 切歌 | `♪ Song: %s`（wesing、applemusic）、`♪ song: %s - %s`（cloudmusic、qqmusic）、`♪ Song: %s - %s (hash: %s)`（kugou）、`♪ Song: %s - %s (id: %s)`（sodamusic） | `♪ 歌曲: …` | 六家全有（applemusic 在 `announce`，其余在各自的 `runSession` 里），但参数不同：wesing 只有 title，applemusic 是拼好的「歌手 - 歌名」（顺序与 cloudmusic/qqmusic/kugou/sodamusic 的「歌名 - 歌手」相反），kugou 多带 hash，sodamusic 多带 id |
| 暂停 / 恢复 | `paused @ %.2fs` / `resumed @ %.2fs` | `暂停 @ %.2fs` / `恢复 @ %.2fs` | cloudmusic / qqmusic / kugou / sodamusic 四家的 `runSession`，applemusic 的 `onTwin` |
| seek | `Seek-back detected: %.2fs → %.2fs` / `forward seek detected: %.2fs → %.2fs` | `检测到回跳: …` / `检测到前跳: …` | cloudmusic / qqmusic / kugou / sodamusic 四家的 `runSession`，applemusic 的 `onTwin`；wesing 只有回跳 |
| 对表 | `synced to UI progress: %.2fs → %.2fs` | `按界面进度对表: %.2fs → %.2fs` | 只有 cloudmusic 的 `runSession`：单次校准量达到 0.2s 才打，写校准前后的位置；不到 0.2s 的校准不打日志。它反复出现说明 DOM 跳秒时刻不稳（§7.9） |
| 歌词加载完成 | `Lyrics loaded: %d lines; per-character: %s`；cloudmusic 为 `lyrics loaded (CDP\|Redux\|API): …`，qqmusic 的补取路径为 `Lyrics loaded (backfill): %d lines; per-word: %s` | `歌词加载完成[(来源)]: %d 行；逐字：<否\|是>` | 六家全有；来源后缀只有 cloudmusic 用（`(CDP)`/`(Redux)`/`(API)`），qqmusic 的补取路径为 `(backfill)`（中文「(补取)」），其余无后缀 |
| 进程等待 | `Waiting for WeSing.exe to start...` / `Waiting for KuGou to start...` | `等待 WeSing.exe 启动...` / `等待酷狗音乐启动...` | wesing.go 的 `waitForProcess`、kugou/watchdog/watchdog.go 的 `waitForKuGou` |

**已知不一致（属 6.1 的「靠人」缺口，不是机制例外）**：wesing 发 `EventPlaybackPause`/`Resume`（wesing.go 的 `pollLyrics` 冻结判定处）却**不打任何 `paused @`/`resumed @` 日志**，也没有前跳检测（`pollLyrics` 里只有回跳检测）。wesing 手里有 playTime，做得到——这是漏的，不是机制决定的。

**英文原文的措辞不一（issue #61 改向留下的，同属 6.1 的缺口）**：改向时英文原文逐条取自原先的英文译文、一字未改，以保证英文环境下的输出不变。那批译文跨播放器并不一致：「逐字：」有 `per-character: ` / `per-word: ` / `word-by-word: ` 三种，切歌有 `♪ Song: ` 与 `♪ song: `，「歌词加载完成」有 `Lyrics loaded` 与 `lyrics loaded`，回跳与前跳一个是 `Seek-back detected`、一个是 `forward seek detected`（上表所列，issue #61 改向后逐条核实）。中文环境下它们照旧一致（译表里的中文没有动）。按英文原文检索时把这些写法都带上；统一它们会改变英文环境下的输出，须另行决定。

### 6.4 i18n（中英双语）：新增用户可见文案的约定

运行期输出按 **Windows 显示语言**中/英切换：`main` 启动早期 `i18n.SetLanguage(i18n.DetectSystemLanguage())` 一次性设定（主语言是中文即中文、否则英文；**只看显示语言，不看区域/时区**）。**英文是源语言**（issue #61 起）：调用点上写英文原文，`i18n/messages*.go` 的 `chinese` 表是「英文原文 → 中文」。英文环境下 `i18n.T` 恒等返回原文；中文环境下查表，查不到回退英文原文。**新增任何用户可见的文案都要按下面接线，否则中文系统上那条就漏成英文**（安全回退、但不完整，且不报错）。
issue #61 之前方向相反（中文原文作 key、`english` 表为译表）。改向时调用点与条目逐条对调，没有改写任何一句，两种语言下的输出与改向前逐字相同（`tools/i18nrekey -baseline` 逐字面量比对过）；代价是英文原文沿用了原先译文里跨播放器不一致的措辞（§6.3 末）。未调用 `SetLanguage` 时是中文（`i18n.Lang` 的零值），测试不设语言即在中文下跑，与开发机的系统语言无关。
✅ 有门禁：`i18n/placeholders_test.go`（逐条校验译文的 `%`-占位符多重集与原文一致，防漏写/错写导致 `%!s(MISSING)`）；`i18n/catalogcoverage_test.go`（直接交给 logger 与 i18n 的字面量不含汉字、都是译表的键，译表的键不含汉字，范围见本节末「自检」）。

- **① logger 调用（`.Info/.Warn/...`）：调用点写英文原文，译表补中文。** logger 五方法在边界已对 format 串过 `i18n.T`，正文单独格式化之后再接「[模块] [图标] 」前缀：前缀不进格式串，模块名不占格式实参，所以带序号的 `%[n]` 数的是调用方的实参（✅ `logger/bodyformat_test.go`；此前前缀与正文拼成一个格式串、模块名是第一个实参，`%[1]s` 读到的是模块名，英文环境下六条带序号的日志一直输出错的内容）。新增一条日志 → format 写英文，再把「英文 format 串 → 中文」**逐字**加进 `chinese` 表（`messages_p4_log.go` 或 `messages.go`）；漏加、或照旧约定在调用点上写中文，由 `i18n/catalogcoverage_test.go` 拦。两种语言语序不同时用带序号的 `%[n]` 重排，由 fmt 处理。没有可译内容、定为中文环境下原样输出的格式串（如 `vtable: 0x%08X`）在表里写成键与值相同的一条；只剩占位符与标点的（如 `%s`）不必进表。❌ `go vet` 不查 logger 调用点的占位符与实参是否匹配（logger 五方法不是它认得的 printf 包装器，实测），靠人。
- **② 错误文案：用 `i18n.Errorf`，别用 `fmt.Errorf`。** 写作 `i18n.Errorf("failed to …: %w", err)`，format 是英文原文的字符串常量，中文补进表。`i18n/errorf.go` 的英文一支把 format 与实参原样转发给 `fmt.Errorf`，`go vet` 的 printf 分析器据此把 `Errorf` 认作包装器，转去校验**调用点常量 format** 的占位符（实测：调用点写错即报）。❌ 别把它改回「`format = T(format)` 之后再转发」：分析器见到 format 被赋值就不再把它当包装器，调用点写错不报（issue #61 之前是这种写法，对当时的代码实测也不报）。`fmt.Errorf(i18n.T(...))` 不带其余实参时 vet 报「non-constant format string」；带了实参不报，但调用点的占位符没人查——两种都别写。`errors.New("…")` → `errors.New(i18n.T("…"))`。
- **③ 包级 sentinel 错误（`var Err = errors.New("中文")`）：保持中文，别包 i18n.T。** ❌ — 包级 var 在 **init 求值、早于 SetLanguage**，包了会冻结成那时的语言（中文）；且它们靠 `errors.Is` 按**身份**比较、文本只是附带。用户可见的呈现要在别处（如 StatusInfo）本地化，不在 sentinel 上。现存 14 个（kugou watchdog 3 + qqmusic 2 + applemusic mem 2 + audiocap/frame 7；applemusic 的两个文本不外显，`Start` 按 `errors.Is` 分流后另发本地化的状态文案），别新增会外显的。它们不经 `i18n.T`，issue #61 改向没有动它们。
- **④ `StatusInfo`：非歌名状态必带 `Reason` 稳定码 + 本地化 `Detail`。** ❌ — playing/paused 时 `Detail`=歌名、无 `Reason`；其余状态一律 `Detail: i18n.T("英文原文"), Reason: player.ReasonXxx`。`Reason` 是**播放器无关的稳定机器码**（`player.Reason*`，8 个；`no_song` 为 applemusic 新增），消费方与 `openapi.yaml` 按它判断，**取代对 Detail 的字面量匹配**（`Detail` 随界面语言变化）。没有合适现成码就在 `player/player.go` 加一个并同步补 openapi 的 `reason` 枚举。服务端缓存状态时在 `UpdatePlayerState` 里把 `StatusInfo` 逐字段手拷进 `StatusMessage`，`StatusInfo` 加字段要同步改这里：`Reason` 曾漏拷，HTTP `/status_update`、连接补发与 player_switch 的 FullState 都不带 `reason`，只有实时推送那一条带（2026-10-08 补上，✅ `server/statusreason_cache_test.go`，§4）。
- **⑤ 被当数据注入日志的值：在源头包 i18n.T。** 翻 format 串对**注入进 `%s` 的值**无效——如 `detailedFlag` 返回的 `yes` / `no`（中文环境「是/否」）、组名 `prior` / `normal`（「优先/普通」）、`nonEmpty(x, i18n.T("path unknown"))` 的回退值。在**返回/传入处**写英文原文、包 `i18n.T`，并把中文补进表。
- **⑥ 不该经 i18n 的中文（包了反而出错）**：用于**匹配/比较**的中文常量（窗口名如「全民K歌」、歌词过滤词「著作权/版权」、平台提示查找集「纯音乐，请欣赏」、歌名后缀「(伴奏)」）是数据不是 UI；注入 OBS 的 JS 里的中文注释；**仅上报 Sentry** 的 dev-only 文案（`telemetry.ReportOnce(...)`、Sentry scope payload）按项目决策不译。这些字面量仍是中文，issue #61 改向没有动它们。
- **⑦ §0.3 边界**：语言探测走 kernel32（`GetUserDefaultUILanguage`），Windows-only，隔离在 `i18n/detect_windows.go`（`!windows` 侧是桩）。`i18n` 包主体纯 Go，故 `logger`/`config` 可安全依赖它、仍 `GOOS=linux` 可构建。**绝不把语言探测塞进 logger/config；locale 只能由 main 注入。**
- **⑧ 先存进变量再交给 `i18n.T` 的文案：变量里存英文原文。** 现有两处，都在 `bannerconfig.go`：`bannerGlobalLines` 的行格式与 `bannerConfigFileNotes` 的附注。门禁按调用形状扫不到它们，存成中文不会红；这两处由 `bannerconfig_test.go` 在中英两种语言下断言输出（存成中文则英文一例红，实测）。新增这类写法时自带两种语言的断言。

**自检（✅ 部分门禁）**：`i18n/catalogcoverage_test.go` 扫出货代码（非 `_test.go`；跳过以 `.` 开头的目录与 `build`、`tools`、`testdata`），收集**直接作为实参**传给 logger 五方法（format）、`i18n.T`、`i18n.Errorf` 的字符串字面量（含字面量相加）。`TestShippedMessagesHaveNoHan` 断言它们不含汉字；`TestCatalogCoversShippedMessages` 断言它们是 `chinese` 的键，去掉占位符后不含字母与数字的豁免（`catalogExempt`，由 `TestCatalogExemptionIsNarrow` 钉住）；`TestCatalogKeysHaveNoHan` 断言译表的键不含汉字。各条的变异写法记在用例注释里（均实测）。它只按调用形状查直接传入的字面量，**以下仍靠人**：format 先存进变量或经辅助函数转手的扫不到（⑧）；⑤ 那类注入 `%s` 的值有没有包 `i18n.T` 查不出；译文是不是中文、译得对不对不查；不做类型解析，别的类型若有同名方法且首个实参是字符串字面量会被当成 logger 调用（现有的同名调用只有 `http.Error`，首个实参不是字面量）。⑥ 不经这些调用，不在范围内。漏一条只表现为**中文系统上那一行/那个值是英文**，不报错。

**按旧约定写成的代码合入之后**（调用点上是中文、条目是「中文 → 英文」）：两条汉字门禁会红。跑 `go run ./tools/i18nrekey -write`，它把译表里恰有一句英文与之对应的中文字面量换成那句英文、把键含汉字的条目对调，已是英文的不动；再不带参数跑一遍核对，它与门禁同一口径，另列出实参不是字面量的调用点、与译表里的中文同文却不是直接实参的字面量、没有直接实参引用的条目，供人核对（§13.4）。经变量转手的（⑧）由人改。合入后常见的几种情形（✅ 各有用例，`tools/i18nrekey/rewritereuse_test.go` 与 `rewritedupkeys_test.go`）：
- **新写的调用复用了表里已有的中文、没有新增条目**（如 `i18n.T("是")`，表里已有 `"yes": "是"`）：工具从两个方向的条目里找英文，照常改成 `i18n.T("yes")`。
- **同一句中文在表里对应不止一句英文**：工具不猜，这处调用不改，列出各句候选及位置，核对不通过，由人把调用点改成要的那一句。两句英文共用一句中文本身不算问题，没有调用点用到就不报。
- **同一中英对新旧两个方向各留了一条**（合并冲突两边都留）：去掉旧方向的那条，不对调——对调会在一张表里写出两个相同的键，gofmt 不管，编译不过。对调、去重之后一张表里仍有重复的键（新方向的同一条写了两遍）、或键相同而值不同，工具拒绝改写并报出位置。
- **英文相同而中文不同的条目**对调后会撞键，工具遇到即拒绝改写：意思相同的并成一条中文，意思不同的改英文原文，使之可区分。

数字：issue #65 加入覆盖门禁时一次清出 46 处调用点、43 条文案。issue #61 改向时由工具改写调用点 490 处（出货代码 489 处、测试 1 处）、对调条目 452 条，无撞键；经变量转手的 10 处手改；另补键值相同的条目 4 条。译表里有 3 条没有调用点引用（`player/qqmusic` 三条只上报遥测的文案在表里的条目，改向前就无人引用），未清理。
