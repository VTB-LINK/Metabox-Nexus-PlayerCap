## 14. 已知并接受的风险 / 未决事项

### 已知并接受（**有意的，不是待办**）

**effect-ingest 写端有 token、无 Origin 校验。** `/cloudmusicv3/effect-ingest` 写端要求进程内
一次性随机 token（`?t=`，`crypto/rand` 16B、仅内存不落盘；`handleEffectIngest` 在 Upgrade 前用
`crypto/subtle` 常量时间比较、不匹配即 403）。仍共用恒真的 `CheckOrigin`、无回环校验、默认绑
`0.0.0.0:8765`——**写端安全靠 token，不靠 Origin**：WebSocket 不受同源策略约束，局域网设备或主播机
网页能发起连接，但没有 token 过不了鉴权。token 明文存在于注入网易云页面的抓帧脚本里，能读该进程
内存或网易云 CDP/页面者仍可提取——但具此能力者本就能自行抓同一 canvas，无新增暴露。

- **前提**：token 防的是**本机其它软件**（能连端口、伪造 Origin、读用户文件，但无 CDP/页面 JS 权）。
  **多机部署 / 公网暴露 / 播控机在不可信网络时必须重新评估**（0.0.0.0 绑定 + token 明文在页面脚本里）。
- **未保障的假设**：`effect.go` 的注释称「单一生产者（注入脚本只开一条），故不做并发保护」
  ——**没有任何机制保证它**；token 通过后的第二条 ingest 连接进来时行为**未定义**。
- **进程重启后 token 会变**：注入脚本 `captureInjectJS` 有热接管（`__mbxCapV4` 版本门，同时保留 V2、V3 标志让降级时旧脚本能接管本版循环 +
  `window.__mbxCapSetIngest` 切地址、不新起 rAF 循环）。页面里是升级前注入的旧版循环时（没有停止入口、
  每拍只认 `__mbxCapPaused`），本版把 `__mbxCapPaused` 换成读来恒为真的访问器使其空转（服务端的写入
  经 setter 交给本版）、借旧版的切换函数关掉旧 ws，再起本版循环，不 reload 网易云；被接管的旧循环
  此后每拍只读一次这个标志，直到网易云 reload。本版自己的停止入口是 `window.__mbxCapOwner`（换掉即停）。
  ✅ `player/cloudmusic/effect/capturejs_test.go`（只测了 `a5647e8` 那一版旧脚本；更早只有
  `__mbxCapStarted` 的一版同样只认 `__mbxCapPaused`，读代码确认，无用例）。
- **`/service-status` 不再广告 ingest 地址**（端点仍在，注入脚本经 `EffectIngestWSURL()` 内部取址）。
- **硬约束：别照着「去掉 `CheckOrigin`」改，会炸。** 注入脚本跑在 `orpheus://` 源上，恢复 gorilla
  默认的 `checkSameOrigin` 会比较 `orpheus` vs `127.0.0.1:8765` → 403 → ingest 断，OBS 浏览器源
  也可能一起断。**这条恒真的 CheckOrigin 对两条正路都是承重的。** 收紧写端的正确做法是像现在这样
  在 `handleEffectIngest` 里前置 token 校验，不要动共用的 upgrader。

**spotify 只有行级原文歌词，没有逐字、翻译、音译；`spotify-offset` 不单独配置。** 真机（2026-10，Spotify 1.3.4.258）抓到的每一份 `color-lyrics/v2` 响应都是 `syncType=LINE_SYNCED`、`lines[].syllables` 全是空数组，没有任何 `SYLLABLE_SYNCED` 样本，响应里也没有翻译列；项目负责人决定不做逐字、翻译、音译（issue #106 不做）。模板里 `# spotify-offset: -200` 是**注释示例**（`defaultConfigContent` 与随包 `config.yml` 都如此），不写即跟随全局 `-200`；该值经项目负责人确认正合适，不单独对齐（issue #105 不做）。

**封面规范化不处理 EXIF 方向与 ICC 配置文件；非正方形源图居中裁切，小图放大。** `player.CoverDataURI` 重编码的封面（源图不是 800×800 的）：`image/jpeg` 解码时跳过 APP1 与 APP2，重编码后方向标签与 ICC 配置文件都丢失——带方向标签的图以未转正的样子发出，广色域（如 Display P3）的图按 sRGB 显示、颜色偏灰；非正方形源图居中裁成正方形再缩放到 800×800（issue #113），长边两端被裁去、不留边、不变形，取景与随包前端的 `object-fit: cover` 一致，被裁去的部分不再出现在 cover_base64 里；小于 800 的图放大后发糊（120 档放大 6.7 倍）。已是 800×800 的原字节放行，不受影响。项目负责人的决定：非正方形居中裁切（issue #113，2026-10-13 由拉伸改订）；不处理 EXIF 方向与 ICC（issue #101）。applemusic 的缩略图是否带 ICC 未经真机确认。

**WASAPI 会话信号区分不了 WASAPI 独占（issue #115）。** 独占流在会话枚举里同样是 Active，而会话峰值、端点峰值表与进程 loopback 对它全为零（2026-10-13 以测试程序实测），与共享模式下的真静音在这些读数上无法区分，故帧头 `flags` 的 (1, 1) 不能排除独占；后端只报会话事实，不判「独占」，对外文档如实写明（`doc/openapi.yaml` 的 `/audio-ws`「WASAPI 会话信号」）。能判别的候选是对目标端点试开一条共享模式的 `IAudioClient`（独占占用时应返回 `AUDCLNT_E_DEVICE_IN_USE`），要在主播的声卡上额外开流，未验证，设计选定不做（`doc/design/audio-session-signal-design.md` §7）。开发机上各播放器的设置里都没有独占选项，影响限于用户自行把输出设成独占的场景。

### 未决

| # | 事项 | 卡在哪 |
|---|---|---|
| 1 | CI 无任何 `pull_request` 触发器、无质量门禁 | 现有 Linux runner 只能覆盖 §8 表中 exit=0 的那一行（`server` 已因挂 Guard 移出）；`-race` 在 Windows 开发机上即可跑，不再依赖它。现行补偿是 §3.5「打 tag 前在 Windows 上全跑」，靠人 |
| 2 | Windows-only 包的测试 CI 永远跑不了 | 只有 self-hosted Linux runner，Windows runner 留给别的项目。**如实记录，别假装有覆盖** |
| 3 | 持续 WASAPI 进程 loopback 与专业声卡驱动蓝屏的关联 | 2026-09-30 开发机（RME Digiface）蓝屏、报 RME 驱动；持续捕获是候选诱因之一，未证实也未排除。主播机器同样可能用这类声卡，现有缓解只有按需门控（§3.6）。**无法稳定复现，卡在无法定性** |
| 4 | 同一播放器多实例时只捕获 `MainPID` 选中的一个，可能与歌词侧跟踪的实例不一致 | 歌词侧 PID 是会话级局部变量、无 getter；共享判据是更大的接缝，未做（`doc/design/audio-waveform-capture-design.md` §10 已知限制） |
